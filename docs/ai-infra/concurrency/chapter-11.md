# 并发基础：第 11 章 事件驱动并发

第 10 章介绍了非阻塞 I/O：调用不会一直卡在某个 Socket 上。但如果调用快速返回，程序怎样知道哪些连接现在可以继续处理？本章给出的答案是 **I/O 多路复用和事件循环**：操作系统报告就绪的连接，事件循环再调用对应处理逻辑。

## 1. Event：程序要响应的状态变化

**事件（event）**是程序关注的变化或条件，例如新连接到达、Socket 可读/可写、定时器到期或后台任务完成。

- **可读**通常表示现在调用读取不会因“没有数据”而一直等待；监听 Socket 可读可能表示有新连接可接受。
- **可写**表示当前可以发送一些数据，不保证整个响应一定能一次写完。

事件只提供一个触发条件，程序仍需根据事件种类和连接状态决定下一步。

## 2. I/O Multiplexing：一次等待多个连接

**I/O 多路复用（I/O multiplexing）**让一个线程等待多个文件描述符或 Socket 的 I/O 状态。等待结束时，系统返回已就绪对象，程序逐个处理。

可以把它想成接线台：服务员不必站在每部电话旁边等待，而是登记多条线路；有线路响起，接线台通知服务员处理对应线路。

操作系统提供 select、poll、epoll、kqueue 等底层机制。Python 的 selectors.DefaultSelector 会选择当前平台可用的实现，并等待多个文件对象的可读或可写事件。参见 [Python selectors 文档](https://docs.python.org/3.14/library/selectors.html)。

## 3. Event loop：等待、分派、处理，再继续等待

**事件循环（event loop）**持续执行以下工作：

~~~text
注册需要关注的 Socket 和事件
→ 等待操作系统报告就绪事件
→ 找到对应连接和处理器
→ 执行非阻塞读写并更新连接状态
→ 继续等待下一批事件
~~~

每条连接需要保存自己的状态，例如请求是否读完整、响应还有多少字节未写出、当前处于哪个协议阶段。事件循环本身负责等待和调度，不替应用自动完成全部协议流程。

事件处理函数应尽快返回。若回调执行长时间 CPU 计算、同步文件读取或阻塞式网络调用，整个循环线程会被占住，其他连接的事件也不能及时处理。长计算应交给其他执行资源，再通过消息或 Future 把结果交回循环。

## 4. Callback 与 Reactor：把事件接到处理逻辑

**回调（callback）**是交给框架在事件发生时调用的函数。例如可读时调用读取处理器，请求完整后进入业务处理，响应准备好后注册可写事件，再在可写时继续发送响应。

这样可以把流程拆成多个短处理函数，但完整业务路径可能分散在多处。程序要明确保存连接状态、传递错误、处理取消和关闭，避免回调关系难以追踪。

**Reactor 模式**常见步骤如下：

1. 注册要监听的 I/O 对象；
2. 通过事件分发器等待 I/O 就绪；
3. 将就绪事件分派给对应处理器；
4. 处理器进行非阻塞读写并更新状态；
5. 重新注册或继续等待。

Reactor 通知应用“现在可以尝试 I/O”，之后由应用执行读写。**Proactor**的概念模型则是由系统完成异步操作后再通知结果。前者是就绪通知，后者是完成通知。

## 5. 四类 I/O 模型：调用是否阻塞，操作如何完成

同步/异步与阻塞/非阻塞描述不同方面：

- **阻塞/非阻塞**关注当前调用无法继续时，调用线程是否停在调用处。
- **同步/异步**关注调用方是否在调用返回前完成 I/O，还是提交操作后由系统再通知结果。

| 模型 | 调用和完成方式 | 直观理解 |
|---|---|---|
| 同步阻塞 | 调用等到读写操作完成 | 没数据就停在读取处 |
| 同步非阻塞 | 调用立即返回当前结果，应用自行检查或等待 | 暂时不可读就返回，之后再试 |
| 异步阻塞 | 提交操作后，调用方可阻塞等待完成通知 | 系统推进操作，调用方在等待结果 |
| 异步非阻塞 | 提交后先做其他工作，完成时通过事件/回调报告 | 完成通知到达后再处理结果 |

常见事件循环网络服务使用非阻塞 Socket 和多路复用等待就绪。可读表示“现在可以尝试读取”，不表示整条业务已完成。理解就绪和完成的差异，有助于区分 Reactor 与 Proactor。

## 6. 事件驱动的披萨服务

服务器收到订单后交给厨房，然后等待烘烤结果并通知顾客：

~~~text
连接到达 → 读取订单事件 → 解析订单
→ 等待厨房结果 → 准备响应
→ Socket 可写事件 → 发送响应
~~~

一个线程在等 A 客户端数据时，可以处理 B 客户端的可写事件；A 的厨房结果未到时，也能继续处理其他订单。服务不必让一个线程长时间阻塞在每个连接上。

代价是服务器要管理每条连接的读取进度、业务阶段、待写缓冲区、超时和错误。对 I/O 等待占主导、并发连接较多的服务，这种模型可以减少每连接一个线程的需要。

## 7. 事件驱动与消息同步

事件驱动代码常用队列、回调和任务结果传递状态。它减少了多个线程直接修改共享变量的情况，但仍需要保证消息顺序、处理重复或失败，并控制队列积压。

例如“读完整请求”必须先于“执行业务”，“业务结果”必须先于“写响应”。可以让每个连接由一个事件循环或一个明确的消费者拥有，减少多个执行者同时修改连接状态的机会。

## 8. 适用场景与边界

事件驱动适合大量 I/O 等待、单次事件处理短小的服务，例如 HTTP 服务、代理、消息网关和连接管理。它不自动适合所有任务：

- CPU 长计算会阻塞事件循环；
- 回调里调用同步 I/O 仍会阻塞循环；
- 复杂协议状态机需要清楚的状态管理；
- CPU 密集任务应交给线程池、进程池或专用计算服务。

## 9. 本章小结

- 事件表示 I/O 状态、定时器或任务变化。
- I/O 多路复用让线程同时等待多个 Socket 的就绪状态。
- 事件循环持续等待事件并分派处理器；处理器要尽快返回。
- Reactor 通知 I/O 就绪，应用再读写；Proactor 概念模型通知异步操作完成。
- 同步/异步与阻塞/非阻塞是两个维度；可读不等于整条请求已处理完。
- 事件驱动减少大量空闲连接占用线程的开销，但要管理连接状态、事件顺序和错误。

### 面试表达：事件循环怎样用少量线程管理很多连接？

> 服务将 Socket 设为非阻塞，并向 I/O 多路复用器注册可读、可写事件。事件循环等待操作系统报告就绪连接，再分派给对应处理器。处理器执行一小段非阻塞读写、更新连接状态后尽快返回，循环继续处理其他事件。这样等网络数据的连接不必各占一个线程。CPU 密集计算和阻塞调用需要转移到其他执行资源。
