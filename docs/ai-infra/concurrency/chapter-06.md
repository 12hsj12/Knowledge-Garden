# 并发基础：第 6 章 多任务

第 5 章讨论了任务之间如何通信。本章把视角转向计算机如何让多个任务在一组处理器资源上持续推进：先判断工作受 CPU 还是 I/O 限制，再理解多任务和抢占式调度，最后看上下文切换、操作系统调度与任务隔离怎样共同支撑应用运行。

本章的重点不是让一项计算凭空变快，而是理解系统如何在任务等待时安排其他工作，以及如何在响应速度、资源利用和调度开销之间取舍。[本章目录与学习目标](https://livebook.manning.com/book/grokking-concurrency/chapter-6)

## 1. 先判断瓶颈：CPU-bound 与 I/O-bound

### 1.1 CPU-bound：主要时间花在计算

**CPU-bound（计算受限）**的任务，其完成速度主要受处理器计算能力限制。处理器持续执行指令，任务很少因为外部设备而长时间等待。

常见例子包括：

- 对大量数据做哈希、压缩或解压；
- 运行复杂的数值计算；
- 搜索大量候选结果；
- 执行没有调用 GPU 加速的模型或图像计算。

若工作可以拆成相互独立的部分，在多个 CPU 核上并行执行可能提高吞吐；若工作本身依赖串行步骤，增加执行单元的收益会受限。CPU-bound 的判断重点是处理器是否一直忙于有效计算。

### 1.2 I/O-bound：主要时间花在等待输入或输出

**I/O-bound（输入/输出受限）**的任务，完成进度主要取决于文件、网络、数据库、设备或用户输入等外部操作。CPU 可能只做短暂处理，然后等待数据到达或操作完成。

常见例子包括：

- 从磁盘读取文件；
- 等待 HTTP 服务或数据库返回结果；
- 等待键盘、鼠标或其他设备输入；
- 将数据写入文件、网络连接或外部存储。

对 I/O-bound 任务，单纯增加 CPU 算力不会让网络服务更快响应；但如果当前任务等待期间有其他任务可做，系统就可以安排它们使用 CPU。

| 观察维度 | CPU-bound 常见表现 | I/O-bound 常见表现 |
| --- | --- | --- |
| CPU 使用 | 持续较高，主要在执行计算 | 有较多等待区间，CPU 可能出现空闲 |
| 改善方向 | 并行化计算、优化算法、使用合适的处理器 | 减少等待、并发处理多个 I/O、优化外部服务与数据传输 |
| 多任务的帮助 | 单核上交错执行通常不会提高纯计算吞吐；多核和任务并行可能提高吞吐 | 一个任务等待时，其他就绪任务可以利用 CPU，提高整体进展和响应能力 |

### 1.3 怎么识别真正的瓶颈

判断瓶颈时要看任务运行时主要在“做什么”或“等什么”，而不是只看任务名称：

1. 测量端到端耗时，区分 CPU 执行时间和外部等待时间。
2. 观察 CPU 使用率、磁盘与网络吞吐、数据库延迟和队列等待。
3. 看一次请求中各阶段的耗时，找到占比最大的部分。
4. 对混合型任务分别分析阶段：例如读取文件是 I/O-bound，后续压缩文件可能是 CPU-bound。
5. 每次只改变一个关键因素并重新测量，确认优化确实影响了瓶颈。

高 CPU 使用率可能意味着计算量大，也可能意味着线程过多、重复计算或忙等；低 CPU 使用率可能表示任务在等待 I/O，也可能表示工作没有被有效调度。应把运行指标与请求路径、系统调用或阶段耗时结合起来看。[Manning 对 I/O-bound 工作的讲解](https://livebook.manning.com/learn/concepts/i-o-bound-work--domain-concept/grokking-concurrency)

## 2. 多任务：让多个任务在同一系统中持续推进

**多任务（multitasking）**是系统管理多个任务、让它们在一段时间内都能取得进展的方式。多个任务并不一定在同一瞬间执行：

- 在只有一个 CPU 执行资源的情况下，任务可以轮流获得处理器时间，整体表现为交错推进。
- 在有多个 CPU 核或处理器时，多个任务还可以在不同执行资源上同时运行，这才是硬件层面的并行。
- 某个任务等待 I/O 时，操作系统可以暂时不安排它使用 CPU，把处理器分给其他就绪任务。

例如，一个单核设备同时运行音乐播放器、网页服务和文本编辑器。它们通过短时间轮流使用 CPU 来维持交互响应；网络请求等待数据时，CPU 可以处理其他任务。多任务提升的是整体资源利用、响应性或吞吐，不会让某一次磁盘读取或网络传输本身变快。

### 一条时间线看并发与并行

~~~text
单个 CPU 执行资源： 任务 A ── 任务 B ── 任务 A ── 任务 C
                    （交错推进，同一时刻轮流执行）

多个 CPU 核：       核 1：任务 A ───────────
                    核 2：任务 B ───────────
                    （不同任务可以同时执行）
~~~

这和前面章节的区分一致：**并发描述多个任务在重叠时间段内取得进展；并行描述多个任务在不同执行资源上同时运行。**

## 3. 抢占式多任务：时间片用完，系统替换当前任务

### 3.1 抢占的基本过程

**抢占式多任务（preemptive multitasking）**允许操作系统在当前任务没有主动让出处理器时，暂停它并安排另一个可运行任务。

一个简化过程是：

1. 调度器选择一个就绪任务，让它运行一段时间。
2. 计时器中断或其他调度事件到来，操作系统检查是否要切换任务。
3. 当前任务的执行状态被保存；另一个就绪任务的状态被恢复。
4. 后续某个时刻，原任务可以再次获得处理器并从暂停处继续执行。

这一小段可运行时间常称为**时间片（time slice）**。具体调度策略和时间片长度由操作系统、设备和负载共同决定；应用程序不应依赖任务以某个固定顺序或精确时间运行。[Manning 对抢占式多任务的讲解](https://livebook.manning.com/learn/concepts/preemptive-multitasking--technique/grokking-concurrency)

### 3.2 与协作式多任务的区别

| 方式 | 谁决定当前任务何时让出执行权 | 常见例子 |
| --- | --- | --- |
| 抢占式调度 | 操作系统可以暂停当前可运行线程并调度其他线程 | 普通操作系统中的 CPU 线程调度 |
| 协作式调度 | 当前任务在约定位置主动让出执行权 | asyncio 事件循环中的协程在 await 等待时挂起 |

抢占式调度不需要应用代码在每段工作之间主动调用“让出 CPU”；协作式调度则依赖任务按时让出控制权。协作式任务若长时间执行 CPU 计算且没有等待点，会拖住同一事件循环中的其他协程。

两种机制都需要管理任务状态和执行顺序，也都要处理任务之间的依赖。它们的调度层次不同：操作系统调度线程或进程，asyncio 事件循环调度协程。[Python asyncio 任务文档](https://docs.python.org/3.14/library/asyncio-task.html)

## 4. 街机游戏比喻：等待输入时让别的工作推进

想象一台街机只有一个 CPU 执行资源，但它要处理三类工作：

1. 读取玩家按键；
2. 根据当前状态计算游戏世界；
3. 把新画面发送到显示设备。

读取按键可能要等玩家操作，绘制画面也可能等待设备；这些时间里 CPU 不必一直空等。操作系统可以让游戏线程等待，同时安排另一个就绪任务执行。计算游戏世界则主要消耗 CPU，通常会继续使用处理器直到它等待、结束或被调度系统抢占。

这个例子强调了三件事：

- 输入和显示的等待属于 I/O 等待，不能靠加快 CPU 指令直接消除。
- 计算任务在 CPU 忙碌时仍需要处理器时间，调度器决定它什么时候运行。
- 如果系统频繁切换任务，切换本身会产生开销；任务数量和切换频率需要平衡。

比喻帮助理解“等待期间换任务”的动机；实际运行中，操作系统内核负责处理时钟中断、线程状态与调度，不是应用自己用一个计时器强行中断 CPU 线程。

## 5. 上下文切换：先保存现场，再恢复另一项工作

**上下文切换（context switch）**是处理器从执行一个线程或进程转向执行另一个时，保存当前执行状态并恢复另一份状态的过程。

执行状态可能包含：

- 程序计数位置：下一步要执行哪条指令；
- 通用寄存器及相关处理器状态；
- 栈指针和线程运行状态；
- 操作系统用于恢复任务的信息。

通过保存和恢复现场，被暂停的任务之后可以从原来的位置继续执行。线程切换通常要切换线程自己的执行状态；若切换到另一个进程，还可能涉及进程地址空间和其他资源管理状态。具体开销随处理器、操作系统和切换场景而变。

切换使有限的 CPU 能被多个任务轮流使用，但它本身不处理业务工作。调度过于频繁时，保存状态、恢复状态和相关缓存效应会占去更多资源；切换太少又可能影响其他任务的响应。因此性能分析要看有效工作、等待和调度开销的整体比例。[Manning 对上下文切换的讲解](https://livebook.manning.com/learn/concepts/executioncontext--api-element/grokking-concurrency)

## 6. 多任务运行环境：操作系统、隔离与调度

### 6.1 操作系统负责安排 CPU 任务

应用创建进程或线程后，操作系统维护它们的可运行状态，并由调度器从就绪任务中选择合适的执行对象。一个任务可能处于：

- **运行**：当前正在 CPU 上执行；
- **就绪**：具备运行条件，等待被调度；
- **阻塞/等待**：等待 I/O、锁、事件或其他条件，暂时不能继续运行。

等待条件满足后，任务通常回到就绪状态。这个模型与第 4 章介绍的进程和线程状态衔接起来：任务阻塞不代表整个应用中的所有任务都必须停止。

### 6.2 任务隔离决定错误和资源如何相互影响

进程为运行中的程序提供地址空间和资源边界。不同进程通常不能直接读写对方的普通私有内存，因此进程崩溃或错误写入更容易被限制在自己的边界内；需要通信时，就通过 IPC、Socket、文件或外部服务交换数据。

同一进程中的多个线程共享地址空间和许多进程资源。共享能让数据传递直接，但一个线程对共享对象的错误操作可能影响其他线程。因此隔离强度、通信成本和数据共享便利性需要一起考虑。

在设计服务时，进程数不是越多越好：多进程可以利用多个 CPU 核并提供独立地址空间，但也会增加内存消耗、启动和 IPC 管理；线程便于共享进程内对象，但共享状态需要同步。

### 6.3 调度是操作系统的策略，不是应用的固定顺序

调度器会在响应速度、吞吐、公平性和优先级等目标间进行取舍。任务什么时候开始、运行多久、被哪个 CPU 核执行，都可能随系统负载改变。

因此：

- 不要依赖线程或进程每次都按相同顺序运行；
- 若任务之间有数据依赖，应显式建立通信和同步关系；
- 若任务对延迟敏感，要测量端到端等待和排队时间；
- 若任务数量过多，要留意调度、内存和上下文切换成本。

## 7. 放到 Python 与 AI 服务中理解

### 7.1 I/O 密集服务：多任务减少等待造成的空档

API 服务通常需要等待网络请求、数据库或文件系统。对于阻塞式 I/O，可以让多个线程或进程分别处理请求；一个执行单元等待时，操作系统能调度其他就绪执行单元。对于非阻塞 I/O，事件循环可以在协程等待时运行另一个协程。

~~~python
import asyncio

async def wait_for_service():
    await asyncio.sleep(1)  # 模拟非阻塞 I/O 等待，协程在此让出事件循环

async def main():
    await asyncio.gather(
        wait_for_service(),
        wait_for_service(),
    )

asyncio.run(main())
~~~

这两个等待任务可以重叠推进；示例并没有把 Python 计算分摊到两个 CPU 核。若在协程里直接运行很长的 CPU 密集型循环，而且中间没有 await 或其他让出点，事件循环就无法及时调度其他协程。

### 7.2 CPU 密集服务：计算并行需要合适的执行资源

对标准 GIL 构建下的 CPython，纯 Python 字节码的 CPU 密集任务通常可以评估 ProcessPoolExecutor 或多进程，让多个进程运行在不同 CPU 核；线程更适合需要共享对象或等待 I/O 的场景。会释放 GIL 的原生计算库和 free-threaded Python 构建有不同表现，选择时要结合实际构建与测量。[Python 并发执行概览](https://docs.python.org/3.14/library/concurrency.html)

若任务本质是大量矩阵或张量计算，也可能将可并行计算提交到 GPU。GPU 的线程层级和调度模型属于设备端执行模型，与本章讨论的操作系统 CPU 多任务相关但不同，可参见 [GPU 执行模型、内存层级与性能分析](../gpu/cuda-execution-memory-performance.md)。

## 9. 本章记忆卡

- CPU-bound 任务主要受计算能力限制；I/O-bound 任务主要受设备或外部服务等待限制。
- 多任务让多个任务在一段时间内持续推进；单个 CPU 执行资源通过交错运行实现时间共享，多核才能同时执行多个 CPU 任务。
- 抢占式调度允许操作系统暂停当前线程并运行其他就绪任务；协作式调度要求任务主动让出控制权。
- 任务等待 I/O 时，操作系统可以暂时安排别的就绪任务；这提高资源利用，不会加快那次 I/O 本身。
- 上下文切换保存当前执行状态、恢复另一任务的状态；切换支持时间共享，也会占用资源。
- 进程提供地址空间和资源隔离，线程共享进程资源；隔离、共享便利和 IPC 成本需要一起权衡。
- 任务的执行次序和时间由运行时与操作系统调度，程序应该显式表达依赖与同步。
- asyncio 的事件循环按协作方式调度协程；操作系统以抢占方式调度 CPU 线程，两者作用层次不同。

### 面试表达：多任务怎样提高系统利用率？上下文切换是什么？

> 多任务让多个工作在同一系统中交错或并行推进。一个任务等待网络、磁盘或用户输入时，操作系统可以把 CPU 分给其他就绪任务，从而提高资源利用和系统响应；单个 CPU 核上的纯计算任务交错运行不会因此获得并行吞吐，真正并行需要多个执行资源。抢占式调度允许操作系统通过时间片和调度事件暂停当前线程并选择另一个任务。上下文切换会保存当前执行状态并恢复下一任务的状态，因而能实现时间共享，同时也产生调度开销。分析性能时，我会先判断瓶颈在计算还是 I/O 等待，再结合线程/进程数量、排队时间和切换成本选择并发模型。
