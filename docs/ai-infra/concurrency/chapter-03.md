# 并发与计算机体系结构：第 3 章 计算机如何工作

本章从程序实际运行的硬件出发，解释处理器怎样执行指令、缓存怎样缩短取数等待、运行时和操作系统怎样管理程序，以及并行硬件有哪些组织方式。理解这些内容，能帮助我们判断一项工作适合怎样的处理器，也能看懂 AI 服务中 CPU、GPU、内存和调度之间的关系。

章节主线与 [Manning liveBook 的第 3 章目录](https://livebook.manning.com/book/grokking-concurrency/chapter-3)一致：Processor、Cache、CPU execution cycle、Runtime system、Design of computer systems、Multiple levels of concurrent hardware、SMP、Flynn 分类和 CPU vs. GPU。

## 1. 处理器：程序指令在哪里执行

程序中的加法、比较、跳转、读写数据等操作，最终都会被处理器执行。CPU（中央处理器）是通用处理器；一颗 CPU 芯片通常包含多个核心，一个核心内部又有执行整数、浮点和向量运算的单元。

可以先用下面这条路径建立直觉：

1. **寄存器**暂存当前指令马上要用的数据和中间结果。
2. **执行单元**完成加法、乘法、比较等具体操作。
3. **控制逻辑**决定指令从哪里来、如何解释，以及接下来执行哪些指令。
4. **缓存和内存系统**为执行单元提供数据。

核心的目标不只是“做一次运算”，还要持续从内存层级取得指令和数据，让执行单元尽量保持工作。

### 时钟周期和指令不是一回事

处理器时钟提供一个节拍。假设处理器频率为 2 GHz，表示每秒约有 20 亿个时钟周期；它不表示每个周期都恰好完成一条指令。不同指令所需周期数不同，内存访问也可能经历多个层级。

因此，性能不能只看主频。还要看每个周期能完成多少工作、处理器是否能并行安排多条指令、数据能否及时送到，以及程序中有多少串行依赖。

## 2. Cache：把常用数据放在离处理器更近的地方

CPU 运算速度很快，主存容量大，却比处理器内部的存储层级慢。若每次运算都要等待主存，执行单元会空等。缓存（Cache）在处理器与主存之间保存近期或可能再次使用的数据，降低平均取数时间。

常见的存储距离可以粗略理解为：

| 存储层级 | 位置与作用 | 直观特点 |
| --- | --- | --- |
| Register（寄存器） | 核心内部，保存当前计算直接使用的值 | 最近、最快、容量最小 |
| L1 Cache | 通常靠近单个核心 | 很快、容量较小 |
| L2 Cache | 通常服务一个核心或一组核心 | 比 L1 大，访问稍慢 |
| L3 / LLC | 常由多个核心共享，具体取决于架构 | 容量更大，访问路径更远 |
| DRAM（主存） | 处理器外部的内存条 | 容量大，延迟高于片上存储 |

具体的缓存层级、大小和共享方式因处理器而异。缓存通常以 **cache line（缓存行）**为单位搬运数据，而不是只取程序眼前的一个字节。

### 缓存为什么容易命中：局部性

缓存利用程序常见的两种数据访问规律：

- **时间局部性**：刚访问过的数据，很可能很快再次访问。比如循环中的累加变量。
- **空间局部性**：访问一个地址后，附近地址也可能被访问。比如按顺序扫描数组。

当请求的数据已经在某级缓存中，就是 **cache hit（缓存命中）**；缓存没有所需数据，需要从更低层取回，就是 **cache miss（缓存未命中）**。缓存未命中可能让处理器等待数据，程序表现为“算术操作很少，但运行时间仍然很长”。

一个直观例子是按连续顺序遍历数组。相邻元素通常会一起进入缓存，后续读取能重复利用这批数据。若访问顺序跳跃、数据集合远大于缓存，命中率可能下降，处理器就会更频繁等待主存。

多核系统还需要让不同核心看到一致的共享数据视图。硬件会使用缓存一致性机制协调缓存副本；频繁写入同一份共享状态会增加协调流量和等待。这也是并行程序除了计算量，还要考虑数据摆放和共享方式的原因。

### 对 AI Infra 的意义：看数据是不是跟得上计算

AI 推理中，矩阵运算可能很快，但数据准备、内存访问、设备间搬运和批次组织也会影响端到端耗时。做性能分析时要区分：

- 执行单元忙于计算；
- 处理器在等待缓存或主存；
- CPU 与 GPU 之间正在传输数据；
- 请求在队列中等待调度。

理解缓存和局部性后，“提升算力”就不再是唯一思路；减少重复搬运、改善连续访问和让数据靠近计算单元，也可能带来收益。

## 3. CPU 执行周期：从指令到结果

用于入门的 CPU 执行周期可以概括为：

1. **取指（Fetch）**：从内存层级读取下一条指令。
2. **译码（Decode）**：识别指令类型、操作数和目标。
3. **执行（Execute）**：由相应执行单元完成运算或地址计算。
4. **访存（Memory Access）**：需要时读取或写入数据。
5. **写回（Write Back）**：把结果写入寄存器或其他目标位置。

例如执行 `c = a + b`，处理器需要取得指令，读到 `a` 和 `b` 的值，执行加法，再把结果保存到 `c` 对应的位置。

这是一种帮助理解的流程图。现代 CPU 会通过流水线让多条指令处于不同阶段，也会根据数据依赖和分支情况调整指令安排；因此实际执行不是一条指令做完所有阶段后，下一条才开始。流水线的目标是提高单位时间完成的指令数量（吞吐），而不是保证每条指令的延迟都按比例缩短。

### 延迟与吞吐再区分一次

- **延迟**：单条指令或单个任务从开始到完成用了多久。
- **吞吐**：单位时间内完成多少条指令或多少个任务。

流水线、多个执行单元和多核可以提高整体吞吐；某一条存在数据依赖的指令仍需等待前一步结果。因此分析性能时，既要看单个关键操作的等待，也要看整个系统能否持续处理工作。

## 4. Runtime system：程序运行所依赖的管理层

“运行时系统”（runtime system）指程序运行期间提供支持的一组软件机制。它会随语言和执行环境变化，不是一个固定的单独程序。理解时可以把职责拆成几层：

| 层次 | 主要工作 | 例子 |
| --- | --- | --- |
| 编译器 / 解释器 | 把源代码转换为机器能执行的形式，或逐步解释执行 | C/C++ 编译器、Python 解释器 |
| 语言运行时 | 支持语言特性和程序执行 | Python 虚拟机、内存管理、异常处理 |
| 操作系统 | 管理进程与线程、虚拟内存、文件和设备访问 | Linux、Windows |
| 驱动与设备运行时 | 让主机程序配置和使用特定硬件 | CUDA 驱动与 CUDA Runtime |

例如，Python 程序由解释器执行；操作系统负责给进程分配资源并调度线程；CUDA 主机代码可以通过 CUDA API 把数据传到 GPU、启动 GPU kernel，再等待或查询执行结果。NVIDIA 将 CPU 一侧称作 host，将 GPU 一侧称作 device；host 代码通过 CUDA API 管理数据传输和 GPU 工作的启动。[CUDA 编程模型](https://docs.nvidia.com/cuda/archive/13.4.2/cuda-programming-guide/01-introduction/programming-model.html)

实际程序中，这些层次会协作：应用提出工作，运行时和操作系统管理执行与资源，驱动连接硬件，CPU/GPU 执行指令。区分它们有助于定位问题：错误可能在应用逻辑、语言运行时、操作系统资源、设备驱动或硬件执行的不同环节。

## 5. 计算机系统设计：让硬件适合目标工作

硬件架构是在不同目标之间做取舍，例如：

- 单个核心尽可能快速地处理复杂任务；
- 用更多核心处理更多相互独立的任务；
- 增大缓存，减少访问主存的等待；
- 增加内存带宽，让更多数据及时到达计算单元；
- 加入向量单元或专用加速器，提高特定类型计算的效率。

没有一种设计能让所有工作都达到最优。处理器的选择要结合任务形态：任务是单线程还是可拆分，数据访问是否连续，计算量与数据搬运量如何，程序能否利用对应硬件。

## 6. 并行硬件有多个层次

并行工作可以发生在不同粒度上。由近及远，可以这样理解：

1. **指令级并行**：一个 CPU 核在满足依赖条件时，重叠或并行安排多条机器指令。
2. **向量级并行（SIMD）**：一条向量指令对多个数据元素执行相同操作。
3. **多核并行**：同一 CPU 芯片上的多个核心同时运行不同线程或任务。
4. **多处理器 / 多路系统**：多个处理器共同访问共享内存。
5. **多机并行**：多台机器通过网络交换数据并协作。
6. **加速器并行**：GPU 等设备用大量执行单元处理适合并行化的工作。

层次越往外，通常可用资源越多，数据共享和通信的代价也越值得关注。例如，同一个核心里的寄存器操作与两台服务器之间传输数据，距离和协调成本完全不同。

### 多层并行可以同时存在

一项工作可能同时使用多层并行：一个多核 CPU 运行多个线程，每个核心又用向量指令处理多个数字；CPU 再启动 GPU kernel，让 GPU 的大量线程处理张量数据。看见“并行”时，先问清楚它发生在哪一层、数据在哪里、工作如何分派和汇总。

## 7. SMP：多个处理器共享内存协作

**SMP（Symmetric Multiprocessing，对称多处理）**描述一种共享内存系统：多个地位相近的处理器或核心可以运行操作系统和应用线程，并访问同一主存地址空间。操作系统能够把不同线程分派给可用的处理器，线程之间可以通过共享内存交换数据。

这让多线程程序容易共享数据，但共享也带来成本：

- 多个处理器竞争内存带宽或同一共享资源；
- 写入共享数据需要保持缓存一致；
- 锁和同步会让线程等待；
- 处理器增加后，通信和协调成本可能增加。

传统的 SMP 常用 **UMA（Uniform Memory Access，统一内存访问）**描述各处理器访问主存延迟近似一致的模型。多路服务器也可能采用 **NUMA（Non-Uniform Memory Access，非统一内存访问）**：每个处理器有更近的本地内存，访问其他处理器连接的内存代价更高。NUMA 下，线程和内存数据的放置会影响性能。

因此，SMP 表达的是共享内存的组织方式；UMA/NUMA 进一步描述处理器访问内存的代价是否均匀。它与多台通过网络通信的分布式集群不是同一种内存模型。

## 8. Flynn 分类：按指令流和数据流看并行架构

Flynn 分类用两个问题描述计算机组织：

- 同一时刻有一条还是多条指令流？
- 同一时刻处理一份还是多份数据流？

| 类型 | 全称 | 含义 | 直观例子 |
| --- | --- | --- | --- |
| SISD | Single Instruction, Single Data | 一条指令流处理一份数据流 | 简化的单处理器顺序执行模型 |
| SIMD | Single Instruction, Multiple Data | 一条指令同时对多份数据执行同类操作 | CPU 向量指令、向量化数值计算 |
| MISD | Multiple Instruction, Single Data | 多条指令流处理同一数据流 | 少见的分类，常见于理论讨论或特定冗余系统 |
| MIMD | Multiple Instruction, Multiple Data | 多个处理单元各自执行指令、处理数据 | 多核 CPU、多个节点运行不同任务 |

这是一种粗粒度的分类方法。现代设备往往组合多种组织方式：多核 CPU 整体可以按 MIMD 理解，单个核心又可以使用 SIMD 向量指令；多核 GPU 执行大量并行工作，也不能只靠一个标签完整描述。[亚利桑那大学并行计算材料](https://hpcdocs.hpc.arizona.edu/events/workshop_materials/intro_to_parallel_computing/files/IntroToParallel.pdf)对四类的定义有简明示意。

### GPU 的 SIMT 与 SIMD

GPU 编程中常见 **SIMT（Single Instruction, Multiple Threads，单指令多线程）**。程序员看到的是大量线程；硬件把线程组织成组来执行指令。它和 SIMD 都体现了“相似操作作用于多份数据”的思路，但抽象层不同：SIMD 通常显式表达向量操作；SIMT 暴露线程模型，由硬件按组调度线程。

CUDA 中，CPU（host）发起 kernel，GPU（device）执行大量线程；线程组成 block，block 被调度到 SM 上执行。NVIDIA 的 CUDA 模型将网格组织映射到不同规模的 GPU，并由设备执行这些并行线程。[CUDA 编程模型](https://docs.nvidia.com/cuda/archive/13.4.2/cuda-programming-guide/01-introduction/programming-model.html)

## 9. CPU 与 GPU：按工作负载选择

| 维度 | CPU | GPU |
| --- | --- | --- |
| 设计侧重 | 快速处理复杂、分支多、延迟敏感的通用任务 | 高吞吐地处理大量可并行的数据工作 |
| 执行资源 | 核心数量相对少，每个核心能力强、控制逻辑复杂 | 执行单元多，适合同时推进大量线程 |
| 常见工作 | 请求处理、调度、控制流程、预处理、串行逻辑 | 矩阵运算、张量计算、图像和批量数据处理 |
| 适合的目标 | 降低单个任务延迟，处理灵活控制逻辑 | 提高大规模规则计算的总吞吐 |

GPU 的优势常出现在大量相似操作可同时执行时。CPU 的控制和单线程性能适合任务调度、I/O 处理、分支复杂的业务逻辑。CPU 与 GPU 是协作关系：CPU 准备工作并发起计算，GPU 执行合适的并行 kernel，CPU 再处理结果或继续调度。[NVIDIA 对 CPU/GPU 设计取向的说明](https://docs.nvidia.com/cuda/archive/13.1.1/cuda-programming-guide/01-introduction/introduction.html)

### AI 推理服务中的例子

一条推理请求可能经历网络接入、鉴权、排队、输入预处理、CPU 到 GPU 的数据准备、GPU 张量计算和结果后处理：

- CPU 负责服务控制流程、请求组织、排队和调度；
- GPU 负责适合并行执行的模型计算；
- 批处理可以让 GPU 一次处理更多输入，提高设备利用率；
- 数据传输、排队和小批次带来的固定开销，会影响请求总延迟。

所以“用 GPU”本身不能说明系统一定更快。要看计算是否足够大且可并行，GPU 是否能及时拿到数据，工作量能否形成合适批次，以及端到端瓶颈处在哪里。

## 10. 用本章建立 AI Infra 分析框架

面对一个性能问题，可以按以下顺序拆解：

1. **工作是什么**：是大量相同计算、复杂控制逻辑，还是 I/O 等待？
2. **在哪里执行**：CPU 核、向量单元、GPU，还是多台机器？
3. **数据在哪里**：寄存器、缓存、主存、显存，还是通过网络传输？
4. **如何并行**：工作如何拆分、调度、合并？任务之间有何依赖？
5. **瓶颈在哪里**：计算单元、内存带宽、缓存命中率、设备传输、排队或同步？
6. **指标要什么**：降低单请求延迟，还是提高单位时间吞吐？

这套思路把硬件组织与系统表现连接起来。做 AI Infra 时，性能分析不是只看一张算力规格表，而是追踪工作和数据如何经过运行时、处理器、内存与加速器。

## 11. 本章记忆卡

- **CPU**：通用处理器，面向多类工作；一颗 CPU 芯片可以包含多个核心。
- **Cache**：保存近期或附近数据，利用时间局部性和空间局部性减少等待。
- **Cache miss**：需要从更低层存储取数，可能拉长处理器等待。
- **CPU 执行周期**：取指、译码、执行、访存、写回；现代处理器用流水线和多种调度机制重叠工作。
- **Runtime system**：程序运行期的软件支持；语言运行时、操作系统和设备运行时各有职责。
- **SMP**：多个处理器共享内存地址空间；共享数据便于通信，也带来竞争和一致性开销。
- **Flynn 分类**：按指令流与数据流区分 SISD、SIMD、MISD、MIMD。
- **CPU 与 GPU**：CPU 擅长灵活控制和低延迟任务，GPU 擅长大规模数据并行和高吞吐计算。
- **性能分析**：同时检查计算、数据位置、传输、调度、并行粒度和目标指标。

### 面试表达：为什么 AI 系统需要理解 CPU 和 GPU 的分工？

> 我会从工作负载和端到端链路判断 CPU、GPU 的分工。CPU 更适合请求处理、控制流程、调度和分支较多的通用逻辑；GPU 更适合大规模、规则的数据并行计算，例如模型中的矩阵和张量运算。实际推理服务由 CPU 组织请求和准备数据，再把适合的计算交给 GPU。最终性能还受缓存和内存访问、CPU/GPU 数据传输、批处理与排队影响，所以我会结合延迟和吞吐指标定位瓶颈，而不会只根据设备峰值算力判断快慢。
