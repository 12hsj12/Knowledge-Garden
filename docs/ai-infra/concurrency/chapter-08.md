# 并发基础：第 8 章 竞态条件与同步

第 7 章讨论了怎样把工作拆成可并行的任务。本章接着回答一个运行时问题：多个任务同时访问同一份数据时，怎样保证结果仍然正确？

核心链路是：**共享资源 → 交错执行 → 竞态条件 → 同步 → 互斥、信号量与原子操作**。并发带来吞吐机会，也带来对共享状态的协调责任。

## 1. 共享资源：并发任务可能争用什么

**共享资源（shared resource）**是多个线程、进程或任务都能访问的对象。它可以是内存中的变量、缓存、文件、数据库记录、连接池中的连接，或一个有限容量的服务。

共享资源不一定会出问题。若所有访问都是只读，或每个任务操作彼此独立的数据，通常不需要互斥。风险主要来自多个任务并发读写同一个可变状态，尤其是状态之间存在必须同时成立的约束。

例如，账户余额和账本记录要一起更新；会话消息列表需要保持顺序并限制长度；一个连接池的空闲连接数不能超过容量。设计并发逻辑时，先说清楚“哪些状态由谁共享、哪些条件必须一直成立”，再选同步机制。

## 2. Race condition：结果取决于任务交错顺序

**竞态条件（race condition）**是指多个任务竞争访问共享状态，程序结果会随它们的执行时序或交错顺序而变化。

看一个计数器。假设初始值为 0，两个线程都执行一次加一。表面上的一行加法实际包含“读取、计算、写回”几个步骤：

~~~text
线程 A 读取 0
线程 B 读取 0
线程 A 计算 1 并写回
线程 B 计算 1 并写回
~~~

最后结果是 1，而预期是 2。这叫**丢失更新（lost update）**。问题不是加法公式错了，而是“读取—修改—写回”作为一个整体没有得到保护。

~~~python
counter = 0

def increment():
    global counter
    counter += 1  # 复合读改写；多个线程同时执行时需要同步
~~~

另一个常见形式是**先检查再执行（check-then-act）**：

~~~text
if 库存 > 0:
    库存减一
~~~

若两个请求都先读到库存为 1，再各自扣减，检查和扣减之间的间隙就可能让两边都认为自己成功。需要保护的通常是完整业务不变量，而不是只保护某个变量的一次读写。

两种术语需要区分：

- **数据竞争（data race）**通常描述并发读写同一内存位置且缺少同步的执行情形。
- **竞态条件**关注程序结果是否依赖时序。即使底层操作各自安全，多个操作的组合仍可能形成竞态。

## 3. Synchronization：让并发访问遵循共同规则

**同步（synchronization）**是并发任务为共享状态建立协调规则的总称。它可以决定：

- 同一时刻只有谁能进入临界区；
- 资源有多少份、最多允许多少任务同时使用；
- 某个条件未满足时，任务应该等待到何时；
- 写入完成后，其他任务何时可以继续读取。

同步要围绕**不变量（invariant）**设计。不变量是程序必须持续维持的条件，例如“库存不能小于零”“同一会话的消息按时间顺序追加”“同一个缓冲区不能同时被生产者和消费者以冲突方式修改”。

### 3.1 互斥与临界区

**临界区（critical section）**是访问或修改共享状态、需要受到保护的那段代码。**互斥（mutual exclusion）**保证同一时刻最多一个任务进入受保护区域。

Python 的 Lock 可用上下文管理器自动释放：

~~~python
from threading import Lock

counter = 0
counter_lock = Lock()

def increment():
    global counter
    with counter_lock:
        counter += 1
~~~

进入 with 块时获取锁，离开时释放锁，包括遇到异常的情况。锁只保护约定好的代码区域：所有会破坏同一不变量的读写，都要遵守同一套锁协议。只在写入时加锁、读取时绕开锁，仍可能读到不一致状态。

锁的使用原则：

1. **范围尽量小**：只包住必须原子完成的共享状态操作。锁持有期间做网络请求或长时间计算，会让其他任务白等。
2. **所有路径都能释放**：优先使用 with lock，避免异常路径漏掉 release。
3. **嵌套时保持顺序一致**：若任务需要多把锁，规定全局顺序并始终遵守，降低循环等待风险。
4. **先定义锁保护什么**：一个锁对应清楚的状态和不变量，避免保护范围含糊。

Python 标准库中的基本 threading.Lock 是低层互斥原语；等待者被唤醒后的具体先后顺序不作保证。参见 [Python threading 文档](https://docs.python.org/3.14/library/threading.html#lock-objects)。

### 3.2 信号量：管理有限数量的许可

**信号量（semaphore）**内部维护一个许可计数。任务获取许可时计数减少；许可用完后，后续任务等待；任务释放许可时计数增加，等待者可以继续。

它适合表达“最多允许 N 个任务同时使用某类资源”，例如限制并发访问外部 API、数据库连接或某个昂贵的处理阶段：

~~~python
from threading import BoundedSemaphore

api_slots = BoundedSemaphore(5)

def call_external_api():
    with api_slots:
        return send_request()
~~~

这个例子限制最多五个线程同时进入调用区域。BoundedSemaphore 还会在释放次数超过初始许可数量时报告错误，有助于发现许可管理不平衡。

**Lock 和 Semaphore 的关注点不同**：

| 机制 | 表达的规则 | 常见用途 |
|---|---|---|
| Lock | 同一时刻只允许一个任务进入 | 保护一个共享状态的不变量 |
| Semaphore(N) | 同一时刻最多允许 N 个任务进入 | 管理数量有限的并发容量 |

当 N 为 1 时，信号量可以形成单许可限制；如果意图是保护某个临界区，Lock 通常更能直接表达这个意图。参见 [Python Semaphore 文档](https://docs.python.org/3.14/library/threading.html#semaphore-objects)。

### 3.3 条件变量：等待状态变化，而不是持续轮询

**条件变量（condition variable）**让任务在某个条件未满足时睡眠等待。另一个任务改变共享状态后发出通知，等待者醒来并重新检查条件。

典型流程是：

1. 获取与条件变量关联的锁；
2. 条件不成立时调用 wait；wait 会释放锁并让当前任务等待；
3. 状态被改变并通知后，wait 重新获取锁；
4. 再检查条件，满足后继续操作。

条件必须在循环中重查，因为唤醒只说明“有状态变化的可能”，不代表当前线程运行时条件仍然成立。Python 的 Condition.wait_for(predicate) 可以把“等待并反复检查谓词”写得更清楚。参见 [Condition 文档](https://docs.python.org/3.14/library/threading.html#condition-objects)。

## 4. Atomic operations：把单个状态操作做成不可分割步骤

**原子操作（atomic operation）**对其他执行单元表现为不可拆分的单个操作：观察者不会看到它执行到一半的中间状态。底层处理器和并发库可提供原子读写、比较并交换（compare-and-swap）等能力。

原子操作适合短小、明确的状态更新，例如原子计数器。但“单个操作是原子的”不代表一串操作自动具有原子性：

~~~text
读取余额 → 判断余额足够 → 扣款 → 记录交易
~~~

即使其中某个读写是原子的，整个业务流程仍需协调，确保两笔并发交易不会同时基于同一旧余额做出决定。复杂不变量通常用锁或事务来保护，原子操作则适合构建更低层的并发原语或简单状态更新。

Python 的 threading 提供锁、信号量和条件变量等同步原语；业务代码选择它们时，应以需要维护的不变量为中心，而不是把“原子”当作所有并发问题的通用答案。

## 5. 如何从一个并发 bug 推导出同步方案

遇到共享状态问题，可以按下面的顺序分析：

1. **标出共享状态**：哪些数据被多个任务读写？
2. **写出不变量**：并发执行期间必须成立的业务条件是什么？
3. **找出临界区**：哪些步骤必须作为一个整体完成？
4. **选择机制**：单份共享状态用互斥；有限并发容量用信号量；等待状态变化用条件变量；简单独立更新再考虑原子操作。
5. **检查等待关系**：会不会持有一把锁等待另一把？会不会永远等不到通知或许可？
6. **考虑代价**：锁范围是否过大？热点锁是否让任务排队？能否改为每个任务维护局部结果，最后再合并？

对性能而言，“加锁正确”只是第一步。若大量任务争同一把锁，锁会串行化原本能够并行的工作。可以进一步缩小共享状态、按键分区、使用每任务局部累加后归并，或通过消息队列把写入集中到单一消费者。

在 AI Infra 服务中，同类问题会出现在并发请求更新缓存、限制模型服务并发数、共享推理队列、复用连接池和维护会话状态等位置。把状态所有权或队列边界设计清楚，往往比在多处零散加锁更容易维护。

## 6. 本章小结

- 多个任务访问共享可变状态时，执行交错可能导致竞态条件。
- 检查、修改、写回等复合步骤需要作为整体保护，才能维护业务不变量。
- Lock 适合互斥访问；Semaphore 适合管理有限数量的许可；Condition 适合等待状态变化；Atomic operation 适合短小且可定义为单步的状态操作。
- 同步机制带来正确性，也会带来排队、等待和死锁等风险；临界区应围绕明确的不变量设计。
- 竞态控制回答的是“共享状态如何正确访问”；下一章继续讨论多个同步任务如何陷入死锁、活锁或饥饿。

### 面试表达：并发访问共享状态时怎样保证正确性？

> 我会先识别多个任务共享的可变状态，并明确需要持续满足的业务不变量。然后定位那些必须作为整体完成的检查与更新，把它们放进统一的临界区。单份状态使用互斥锁，有限并发资源使用信号量，等待条件变化使用条件变量；对于简单单步更新再考虑原子操作。最后检查锁的持有范围、释放路径和获取顺序，并结合压力场景观察锁竞争和任务等待。
