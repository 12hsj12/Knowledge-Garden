# 并发基础：第 5 章 进程间通信

第 4 章介绍了进程和线程这些执行单元。本章继续看它们怎样交换数据、传递任务和协调先后顺序。并发程序只有把任务之间的依赖和信息传递安排清楚，多个执行单元才能组成一个正确的整体。

本章的主线是：先区分共享内存与消息传递，再理解线程池怎样用任务队列组织一组可复用的工作线程，最后把这些机制放回密码搜索示例中，观察任务拆分、分发和汇总。[本章目录与学习目标](https://livebook.manning.com/book/grokking-concurrency/chapter-5)

## 1. 为什么并发任务需要通信

并发任务有时彼此独立，可以各自完成；有时则需要交换输入、结果或状态。例如：

- 一个任务完成后，另一个任务才能继续；
- 主线程把许多工作项交给后台 Worker；
- 多个 Worker 处理不同数据块，最后由主线程汇总结果；
- 多个执行单元需要共同读取或更新一份状态。

这里涉及两个相关问题：

- **通信（communication）**：把数据或事件从一个执行单元传给另一个。
- **协调（coordination）**：决定谁何时可以继续、何时需要等待，以及操作之间需要遵循什么顺序。

有些通信机制自带一定的等待行为，例如队列暂时没有消息时，消费者可以等待新任务；但“把数据传过去”并不自动保证所有共享状态都安全。多个执行单元同时修改同一块数据时，仍要设计同步规则。共享数据的竞态、互斥锁、信号量和原子操作将在后续章节深入学习。

> 本书把 IPC（Interprocess Communication，进程间通信）作为并发执行单元交换信息的主题来讨论。严格地说，操作系统语境中的 IPC 主要指不同进程之间的通信；同一进程内的线程天然共享地址空间，线程间的通信通常是访问共享对象并配合同步机制。

## 2. 两种通信思路：共享内存与消息传递

可以先用一个问题区分它们：接收方是直接访问同一块数据，还是通过一个通道收到一份消息？

| 思路 | 数据怎样传递 | 主要优点 | 主要代价 |
| --- | --- | --- | --- |
| 共享内存（shared memory） | 多个执行单元访问同一块内存区域 | 交换大型数据时可以避免反复序列化和复制，读取访问直接 | 必须管理并发读写、同步、数据所有权与生命周期 |
| 消息传递（message passing） | 发送方把消息交给通道，接收方从通道读取 | 通信边界清楚，发送者与接收者可以较松耦合，也便于跨进程或跨机器扩展 | 通常需要组织消息格式，可能产生序列化、复制、排队和等待成本 |

可以把共享内存想成多人共同使用一块工作台：拿取数据很直接，但要约定谁可以在什么时候改动工作台。消息传递更像把任务单放进收发箱：发送者交出消息，接收者从箱子取走；双方通过明确的消息内容和通道协作。

这两类方式是沟通模式的抽象。一个具体系统也可能组合使用：例如用队列传递“哪个数据块需要处理”，而多个 Worker 再访问共享内存中的大数据区。

## 3. 共享内存：共同访问一份数据

### 3.1 线程为何容易共享数据

同一进程中的线程共享进程地址空间，因此一个线程创建的对象通常可以被其他线程引用。线程池里的任务队列、共享配置、缓存和结果容器都可能由多个线程访问。

共享的优势是数据可以直接被访问；困难是访问顺序需要明确。例如，两个线程同时执行“读取计数值 → 加一 → 写回”，两次更新可能互相覆盖。单个看似简单的复合操作不一定天然不可分割。

### 3.2 不同进程如何使用共享内存

进程默认各自拥有独立的虚拟地址空间。若要让多个进程访问同一数据区域，需要操作系统或运行时显式创建共享内存，并让参与进程连接到这块区域。Python 提供 multiprocessing.shared_memory 用于不同进程访问同一块共享内存。[Python 共享内存文档](https://docs.python.org/3.14/library/multiprocessing.shared_memory.html)

共享内存适合传递体积较大、访问频繁的数据。例如图像帧、矩阵或批量数值数据，先通过消息告诉另一个进程“数据在哪、长度是多少”，再让接收方读取共享区域，可以减少整块数据在进程间复制的次数。

共享内存也会带来明确的工程责任：

- 哪个执行单元负责创建区域，哪个负责最后释放；
- 多个执行单元能否同时读，哪些写入必须互斥；
- 如何表示数据格式、长度、版本和有效状态；
- 一个进程异常退出时，如何处理未释放的资源。

共享内存减少了部分数据传递开销，但并不自动解决同步、安全和生命周期问题。

## 4. 消息传递：通过通道交换数据

消息传递把数据交给一个通信通道，由接收者从通道获得内容。通道可以是本机操作系统提供的机制，也可以跨网络连接进程。

### 4.1 管道与 FIFO

**匿名管道（pipe）**通常提供一个简单的数据流通道，常用于有关系的进程之间传递数据。在 Shell 中，命令组合例如 producer | consumer 就体现了一个程序把输出接到另一个程序的输入。

**命名管道（FIFO）**有一个可识别的名称或路径，让不同进程可以通过该名称打开通道。它通常用于同一台机器上的进程通信。数据按通道提供的读取顺序流动；应用仍要定义消息边界和处理策略。

管道更像连续的字节流，而不是天然带有“每条消息长度”的数据包。发送方与接收方要约定如何识别一条完整消息，例如固定长度、分隔符或长度前缀。

### 4.2 Socket

**Socket（套接字）**提供端点间的通信接口。Unix Domain Socket 用于同一台机器上的进程通信；网络 Socket 则通过网络地址连接不同机器上的程序。

Socket 的优势是客户端和服务端边界清楚，并且本机通信与网络通信可以沿用相似的编程模型。代价是需要管理连接、协议格式、超时、断开和部分发送等问题。网络通信还要面对延迟、丢包、重试和远端故障。

### 4.3 队列

**队列（queue）**提供“生产者放入任务，消费者取出任务”的模型。它可以在线程之间传递任务，也可以由多进程队列在进程间传递对象。队列通常会处理必要的线程安全或进程间传输细节；具体是否序列化、是否有界、满载时如何处理，取决于所用实现。

队列很适合作为任务调度的入口：生产者只需提交工作项，不必指定由哪个 Worker 执行；空闲 Worker 从队列取出下一项。队列让生产速度和处理速度可以暂时不同步，但队列若无限增长，系统仍会积累越来越多的等待任务，因此需要考虑容量、背压和拒绝策略。

Python 的 multiprocessing.Queue 会对跨进程对象进行序列化；接收方获得重建后的对象，而不是原进程对象的同一份共享引用。[Python multiprocessing 文档](https://docs.python.org/3.14/library/multiprocessing.html)

## 5. 怎样选择通信机制

选择前先明确通信双方的位置、数据规模、延迟目标和故障边界：

| 需求 | 常见选择 | 重点考虑 |
| --- | --- | --- |
| 同一进程内线程需要共享小型状态 | 共享对象，加锁或其他同步方式 | 谁能写、锁的范围、是否会争用 |
| 多个本机进程需要频繁访问大型数据 | 共享内存，并通过控制消息传递元数据 | 数据格式、同步、创建与释放责任 |
| 任务是离散工作项，生产者与消费者需要解耦 | 线程安全队列或多进程队列 | 队列容量、排队延迟、失败重试、任务结果 |
| 两个本机进程需要通过明确端点交互 | 管道、FIFO 或 Unix Domain Socket | 单向或双向、流式或消息式、连接生命周期 |
| 不同机器上的服务要交换请求与结果 | 网络 Socket 或更高层的消息系统/API | 网络失败、超时、认证、重试和协议兼容 |

没有一种方式在所有维度上都最好。共享内存偏向低开销和大数据共享，但程序必须负责协调；消息传递会增加通道与数据封装成本，却能建立清楚的组件边界，也更容易扩展到跨机器通信。

## 6. 线程池模式：用 Worker 重复处理任务

直接为每个任务创建一个新线程，会让线程创建、退出和资源回收变成额外成本；同时，线程数量如果没有上限，系统也可能因过多线程而消耗大量栈内存和调度资源。

**线程池（thread pool）**预先建立一组可复用的工作线程。主线程把任务提交到队列，空闲 Worker 取出任务并执行，完成后回到队列等待下一项工作。

~~~text
主线程 / 任务生产者
        │ submit(task)
        ▼
     任务队列
      ├── Worker 1：取任务 → 执行 → 取下一个任务
      ├── Worker 2：取任务 → 执行 → 取下一个任务
      └── Worker 3：取任务 → 执行 → 取下一个任务
        │
        ▼
   收集任务结果
~~~

线程池把“任务是什么”与“哪个线程来执行”分开：调用者提交工作并取得结果句柄，池负责调度可用 Worker。线程池限制了同时运行的线程数，并通过复用线程减少频繁创建线程的开销。

### 6.1 用 Python ThreadPoolExecutor 理解任务提交

Python 的 concurrent.futures 提供了线程池接口。下面的例子提交五个计算任务，并在任务完成时读取结果：

~~~python
from concurrent.futures import ThreadPoolExecutor, as_completed

def double(value):
    return value * 2

with ThreadPoolExecutor(max_workers=3) as pool:
    futures = [pool.submit(double, n) for n in range(5)]

    for future in as_completed(futures):
        print(future.result())
~~~

- ThreadPoolExecutor(max_workers=3)：创建最多同时运行 3 个任务的线程池。
- submit(function, args)：提交一次函数调用，并返回 Future。
- Future：代表一个正在运行或尚未完成的任务；结果可用时通过 result() 取得。
- as_completed(futures)：按完成顺序逐个产出 Future，所以打印顺序可能不同于提交顺序。
- with 代码块结束时会等待已提交的任务并关闭线程池。

ThreadPoolExecutor 的接口和执行方式见 [Python concurrent.futures 文档](https://docs.python.org/3.14/library/concurrent.futures.html)。

### 6.2 线程池适合什么工作

线程池适合许多需要等待外部结果的任务，例如并发请求多个 HTTP 服务、读取文件或执行阻塞式数据库调用。一个任务等待 I/O 时，另一个 Worker 可以处理其他已就绪任务。

对标准 GIL 构建下的 CPython，纯 Python CPU 密集型计算通常不会仅靠增加线程就获得多个 CPU 核上的 Python 字节码并行执行。若任务主要是纯 Python 计算，可以评估进程池；若计算在会释放 GIL 的原生库中执行，线程也可能并行推进。应根据实际负载测量，而不是把线程池等同于“自动加速”。[Python threading 文档](https://docs.python.org/3.14/library/threading.html)

### 6.3 线程池要管好队列和生命周期

线程池限制的是同时运行的 Worker 数量；如果任务生产速度长期高于处理速度，等待任务仍可能不断积压。工程上还要设计：

- **背压**：队列达到容量后，是让生产者等待、拒绝新任务，还是把任务持久化。
- **异常与结果**：记录失败任务，决定重试、跳过还是向调用者报告。
- **关闭流程**：停止接收新任务，等待或取消待处理任务，最后回收 Worker。
- **任务粒度**：任务太小，调度和通信成本可能超过计算本身；任务太大，则并行分配不均或取消不及时。
- **池内等待**：若所有 Worker 都阻塞等待同一个池中尚未执行的子任务，可能形成死锁。Python 文档列出了这类 Future 相互等待的例子。

## 7. 重看密码搜索：把任务拆开、分发并汇总

书中再次使用密码搜索示例，把前面讨论的并发概念落到完整流程。这里的核心不是某个语言 API，而是任务组织方式：

1. 明确候选字符串范围以及验证规则。
2. 将候选范围切成若干区间，每个区间成为一个工作项。
3. 把工作项提交给可用 Worker 并发检查。
4. 每个 Worker 搜索自己的区间，找到匹配项时返回结果。
5. 主线程等待任务完成，处理结果并汇总耗时。

~~~text
候选空间
    │ 切分成多个范围
    ├── 区间 A → Worker A ─┐
    ├── 区间 B → Worker B ─┼→ 主线程收集结果
    ├── 区间 C → Worker C ─┤
    └── 区间 D → Worker D ─┘
~~~

这些区间相互独立，因而可以并行执行。主线程与 Worker 之间的任务分发和结果回收就是通信；若 Worker 各自只处理自己的候选范围，不共同改写同一个计数器或结果容器，所需的共享状态协调会更少。

密码搜索只是用来演示任务切分和并行执行的教学例子。工程上还要计入任务调度、数据传递、结果汇总和硬件资源限制；切分成更多任务并不保证运行时间按比例缩短。对 Python 纯计算代码，还要将 GIL 对线程并行的影响纳入选择，评估进程池或其他实现。

## 8. 联系 AI Infra 服务中的进程与任务

第 4 章提到，服务可能启动多个进程 Worker。每个进程有自己的 Python 堆和普通全局变量，因此进程 A 更新自己的字典，不会让进程 B 自动看到同一份新值。

在服务中需要跨 Worker 保留或传递状态时，通常会把状态放到进程之外的共享服务或存储中，例如 Redis、数据库或消息系统。应用通过协议与这些服务通信，而不是让不同 Python 进程直接读取彼此的普通内存。Redis 可以承担共享状态存储或队列相关角色；选择哪种能力，要看场景对持久性、消息语义、吞吐、延迟和故障恢复的要求。

线程池则常用于把一组阻塞式工作交给有限数量的线程处理。异步 API 服务也可能通过线程池运行同步库调用，但线程池和 asyncio 事件循环是不同层次的执行机制：线程池调度线程，事件循环调度协程。

## 9. 常见理解误区

1. **把共享内存当作天然安全**：多个执行单元能看到同一份数据，不代表同时读写不会产生冲突。
2. **把消息队列当作无限容量缓冲区**：生产速度持续高于消费速度时，队列会增加内存占用和任务等待时间。
3. **以为线程池等于并行计算**：线程池提供并发任务调度；是否能在多个 CPU 核同时运行，取决于语言运行时、GIL、任务类型和硬件。
4. **以为 Worker 越多越快**：过多 Worker 会增加调度、内存、竞争和上下文切换成本。
5. **忘记消息格式与结果处理**：发送方和接收方必须对数据格式、错误和完成状态有一致约定。
6. **没有关闭池或处理异常**：任务失败、程序退出与资源回收都应有明确策略。
7. **混淆线程间共享与进程间共享**：同一进程的线程共享地址空间；普通情况下，不同进程有各自的虚拟地址空间。

## 10. 本章记忆卡

- 并发任务通信传递数据或事件；协调规定先后顺序和等待条件。
- 共享内存让多个执行单元直接访问同一数据区域，适合频繁访问或大数据，但要管理同步与生命周期。
- 消息传递通过管道、Socket、队列等通道交换消息，边界清楚，可能产生序列化、复制、排队和网络开销。
- 线程池通过“任务队列 + 可复用 Worker”调度工作，限制并发线程数并减少频繁创建线程的成本。
- Future 表示异步任务的结果占位；读取结果时可能等待任务完成，也可能重新抛出任务异常。
- 线程池可以提高 I/O 并发；对标准 CPython 的纯 Python CPU 密集型代码，要考虑 GIL 并评估进程池。
- 密码搜索示例展示了“任务拆分 → 分发执行 → 收集结果”的完整并发流程。
- 通信机制需要结合数据规模、延迟、隔离、故障边界、扩展范围和生命周期选择。

### 面试表达：并发任务之间如何通信，线程池解决什么问题？

> 并发任务之间需要交换输入、结果或状态，也需要协调执行顺序。共享内存让多个执行单元直接访问同一数据，访问开销低，适合高频或大规模数据共享，但要设计同步、所有权和生命周期；消息传递通过队列、管道或 Socket 交换消息，组件边界清楚，也可以扩展到跨进程和跨机器，但要处理消息格式、复制、排队和失败。线程池则把任务提交与线程管理分开：调用方把工作放入调度入口，池中的有限数量 Worker 反复取任务执行，并通过 Future 或其他结果通道返回结果。实际选择还要看任务是 CPU 密集还是 I/O 密集、是否跨进程、队列是否会积压，以及通信成本是否抵消并发收益。

3. 线程池的任务队列满了，系统可以采取哪些策略？
