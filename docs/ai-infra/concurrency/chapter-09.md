# 并发基础：第 9 章 死锁、活锁与饥饿

第 8 章讨论了怎样用同步保护共享状态。本章进一步关注同步设计本身可能造成的进度问题：多个任务会不会互相等待？任务明明在运行，整体却没有前进？某个任务会不会一直等不到资源？

本章按这条主线展开：**哲学家就餐问题 → 死锁 → 破坏死锁条件 → 活锁与饥饿 → 同步设计 → 生产者—消费者与读者—写者**。

## 1. 哲学家就餐问题：局部合理也可能让整体停住

想象几位哲学家围桌而坐，相邻两人之间放一把叉子。每个人吃饭需要同时拿到左右两把叉子。若所有人都先拿左边的叉子，再等待右边的叉子，那么每把叉子都被一个人持有，每个人又在等邻座释放另一把。

每个人的局部动作都合理，组合起来却没有任何人能继续。这就是经典的**哲学家就餐问题（Dining Philosophers Problem）**：它把共享资源、互斥访问、持有资源后再等待以及环形依赖放在同一个例子里。

该问题可对应到工程场景：两个任务分别持有资源 A 和资源 B，却以相反顺序申请对方持有的资源；或者服务请求持有数据库连接后等待另一个连接池许可，而另一请求反过来持有许可等待连接。

## 2. Deadlock：互相等待，所有相关任务都无法前进

**死锁（deadlock）**是多个任务因等待彼此持有的资源或事件而永久阻塞的一种状态。典型现象是：系统中相关任务仍存在，但每个任务都在等待另一个任务先行动。

经典分析使用四个必要条件。它们同时成立时，死锁才可能发生：

1. **互斥（Mutual exclusion）**：某些资源同一时刻只能由一个任务使用。
2. **占有并等待（Hold and wait）**：任务已经持有资源，同时继续等待其他资源。
3. **不可抢占（No preemption）**：系统不能强行把任务已持有的资源取走，只能由任务主动释放。
4. **循环等待（Circular wait）**：存在一条环形等待链，链中的每个任务都等待下一个任务持有的资源。

可以用两把锁说明循环等待：

~~~text
任务 A：先拿 Lock 1，再等待 Lock 2
任务 B：先拿 Lock 2，再等待 Lock 1
~~~

若 A 已拿到 Lock 1、B 已拿到 Lock 2，A 和 B 就互相等待。掌握四个条件的价值在于：设计时只要有意识地破坏其中至少一个条件，就能预防这类死锁结构。

### 2.1 哲学家问题的两种解决思路

#### 仲裁者（arbitrator）

让一个协调者统一决定谁可以开始取用资源。协调者只有在左右两把叉子都可用时，才允许该哲学家进入取用阶段。这样任务不会先占有一把资源、再持有它等待另一把，打破了“占有并等待”。

工程上可以把它理解为资源管理器、队列或集中调度器：请求先向协调者申请完整资源组合，获准后再执行。

#### 资源层次（resource hierarchy）

为所有资源规定一个固定顺序，并要求每个任务都按同一顺序申请。比如资源按编号从小到大获取，释放时再反向释放。

~~~text
任务需要资源 2 和资源 7：
先获取资源 2，再获取资源 7
~~~

所有任务都沿相同方向等待，无法形成资源编号不断递增又回到起点的环，因此破坏了“循环等待”。这个办法适合资源集合可排序、各路径都能遵守同一规则的场景。

~~~python
# 示意：first_lock 与 second_lock 按稳定的全局顺序确定
with first_lock:
    with second_lock:
        update_shared_state()
~~~

关键是所有调用路径使用同一排序规则，而不是只在某一处按顺序申请。

## 3. Livelock：任务在响应，但整体没有进展

**活锁（livelock）**中，任务没有像死锁那样全部阻塞；它们仍在运行、释放和重试，但彼此的反应让有效工作一直无法完成。

例如两名行人都想礼让对方，于是同时向左让；发现路线仍冲突后又同时向右让，反复重复“让路—重试”，却没有人真正通过。并发程序里，两个任务发现资源冲突后同时释放、等待同样时间、再同时重试，也可能一直重复冲突。

缓解活锁可以引入非对称规则、随机退避、重试上限或集中仲裁。随机等待的作用是打破任务“同步地一起重试”的节奏；重试达到上限后应返回可处理的错误或进入队列，而不是无限循环。

## 4. Starvation：系统在前进，但某个任务长期得不到机会

**饥饿（starvation）**是某个任务持续无法获得所需资源或调度机会，而其他任务仍能不断完成工作的情况。

例如一个锁每次释放后都唤醒某个更容易抢到锁的请求，另一个请求长期排在后面；或者高优先级任务不断到来，使低优先级任务一直得不到 CPU 时间。系统总体有进展，所以这不是死锁；问题在于进展没有公平分配给所有等待者。

常见改进方法包括：

- **公平队列**：按请求到达顺序授予资源。
- **有界等待**：限制一个任务在获准前最多被其他任务越过的次数。
- **优先级老化（priority aging）**：等待越久，调度优先级逐渐提高。
- **合理设置资源配额与超时**：避免单个任务长期占用稀缺资源。

公平性可能降低吞吐或增加调度成本，因此要结合业务目标权衡。比如严格 FIFO 能减少饥饿，但有时会让后到的短任务排在一个耗时很长的请求后面。

## 5. 三种进度问题放在一起看

| 问题 | 任务表现 | 整体是否有进展 | 典型原因 |
|---|---|---|---|
| Deadlock 死锁 | 相关任务阻塞等待 | 没有 | 任务形成循环等待 |
| Livelock 活锁 | 任务持续响应、重试 | 没有有效进展 | 对称地让步和重试 |
| Starvation 饥饿 | 某个任务长期等不到资源 | 其他任务仍在进展 | 资源分配或调度长期偏向其他任务 |

排查时观察任务状态和等待链：线程都阻塞且互相等待，优先检查死锁；线程活跃但重复重试，检查活锁；服务吞吐正常而某些请求等待时间持续异常，检查饥饿和公平性。

## 6. Designing synchronization：先设计资源协议，再写锁代码

可靠的同步设计需要同时考虑**互斥正确性**和**任务进展**：

1. **列出资源与所有权**：哪些资源需要互斥？一次任务可能同时持有哪些资源？
2. **画出等待关系**：任务持有资源 X 时会等待什么？所有路径的锁获取顺序是否一致？
3. **定义失败与取消路径**：超时、异常、取消时，已获取的资源如何释放？被唤醒后要重新检查什么条件？
4. **缩短持有时间**：尽量不要拿着锁等待网络、磁盘或用户输入等慢操作。
5. **决定公平性策略**：队列顺序、优先级和超时是否符合业务要求？
6. **观察进展**：记录请求等待时间、锁等待、队列长度、重试次数和超时，让“卡住”变成可定位的数据。

从系统设计角度看，减少共享和明确消息边界往往比大量使用锁简单。例如把任务放入线程安全队列，由一个消费者负责修改某份状态；或者每个任务先计算局部结果，再由汇总阶段合并。这与第 5 章的消息传递和第 7 章的任务分解相连：好的并发结构能减少需要协调的共享状态。

## 7. Producer-consumer：用队列连接生产速度与处理速度

**生产者—消费者（producer-consumer）**模式中，生产者产生工作项并放入缓冲区，消费者从中取出并处理。队列负责保存尚未处理的任务，也提供双方之间的同步边界。

- 队列为空时，消费者等待新任务。
- 有界队列已满时，生产者等待空间，形成**背压（backpressure）**，避免生产速度过快导致内存无限增长。
- 多个消费者可并行处理彼此独立的工作项。

Python 的 queue.Queue 为多线程生产者和消费者提供线程安全队列，并能用 maxsize 限制缓冲区容量：

~~~python
from queue import Queue

jobs = Queue(maxsize=100)

def producer(items):
    for item in items:
        jobs.put(item)  # 队列满时等待，给下游施加背压

def consumer():
    while True:
        item = jobs.get()  # 队列空时等待
        try:
            process(item)
        finally:
            jobs.task_done()
~~~

这个例子中的队列容量是 100：它平滑短时的生产/消费速度差异，同时把最大待处理任务数限制在可控范围。实际程序还需要定义停止信号、错误重试和关闭流程；每个消费者都要能收到结束信号。参见 [Python queue 文档](https://docs.python.org/3.14/library/queue.html)。

## 8. Readers-writer：读共享，写互斥

**读者—写者（readers-writer）**问题描述一份共享数据被多个任务读取、也会被任务修改的情况：

- 多个读者只读取数据时，可以并发访问。
- 写者修改数据时，需要独占访问，避免读者看到一半更新的状态，也避免多个写者互相覆盖。
- 读写协调策略会影响公平性。

若策略持续优先放行读者，新到读者不断加入，写者可能一直等不到没有读者的时机；若总是优先写者，读者也可能被长期延后。工程实现要明确采用读者优先、写者优先还是相对公平的策略，并检查它对等待时间和吞吐的影响。

缓存配置、模型元数据、路由表等数据常见“读多写少”的模式。可以使用读写锁或不可变快照等设计；选型取决于更新频率、对象大小、读写延迟目标和语言运行时提供的工具。

## 9. 放到 AI Infra 服务里理解

这些概念能连接到服务运行中的实际问题：

- **模型推理并发**：服务通常要限制同时进入 GPU 的请求数；信号量或调度队列可以控制容量，并让过载请求排队或快速返回。
- **共享缓存与会话状态**：多个请求同时更新同一条记录时，需要原子更新、数据库事务或明确的所有权策略，避免丢失更新。
- **工作队列**：在线 API 接收请求，后台 Worker 执行耗时任务；有界队列能提供背压，队列长度和等待时间反映系统拥塞。
- **模型与配置读取**：读者—写者思路可用于分析频繁读取、偶尔更新的数据。更新应有清晰的一致性边界。
- **故障排查**：死锁看锁等待图和线程栈；活锁看高频重试却无完成量；饥饿看个别任务等待时间与整体吞吐之间的差异。

这些模式的共同目标是让任务既正确访问资源，也能在容量和公平规则下持续推进。

## 10. 本章小结

- 死锁来自任务间的循环等待；通过统一资源层次、仲裁或其他手段破坏死锁必要条件，可以预防。
- 活锁中的任务持续活动，却因为相互反应无法完成有效工作。
- 饥饿表现为部分任务长期得不到资源，而系统其他部分仍然前进。
- 生产者—消费者通过队列把工作生产和处理解耦；有界缓冲区能控制积压并向上游施加背压。
- 读者—写者需要同时考虑读写互斥与等待公平性。
- 同步设计不仅要回答“数据是否正确”，还要回答“等待何时结束、进度是否公平、系统怎样观察拥塞”。

### 面试表达：怎样预防并排查死锁？

> 我会先画出任务和资源的持有、等待关系，重点检查多个资源是否以不同顺序获取。预防上可以规定全局锁顺序、通过仲裁一次申请完整资源集合，或减少嵌套锁和共享状态。实现时保证异常、超时与取消路径释放资源，并缩短持锁时间。排查时查看线程栈和等待链；若线程处于阻塞且构成环，优先处理死锁；若线程持续重试但没有完成量，检查活锁；若整体吞吐正常而个别请求长时间等待，检查资源分配是否造成饥饿。
