# 并发基础：第 1 章 引入并发

本章先回答两个问题：为什么计算机需要并发？系统性能应该从哪些角度衡量？书中把并发放在更大的系统视角下讲，涉及性能、复杂任务、可扩展性和不同层次的并发。[本书章节提纲](https://livebook.manning.com/learn/grokking-concurrency)

## 1. 为什么要学习并发

现实中的工作经常同时发生：服务端会同时收到多个用户请求，数据平台会持续处理多个分区，推理系统可能要服务多个模型调用。计算机若总是完成一个完整任务后才开始下一个任务，等待和资源空闲会拖慢整个系统。

并发的核心思路是把工作拆成多个可以独立推进的任务，让它们在重叠的时间段里取得进展。系统可以交替运行这些任务，也可以让多个计算资源同时执行它们。

并发的意义主要体现在：

- **提高资源利用率**：一个任务等待网络或磁盘时，处理器可以推进其他任务。
- **提高系统处理能力**：多个独立工作可以分担到更多资源上。
- **处理更大或更复杂的问题**：将任务拆开后，系统能在不同资源上协作完成。
- **支持系统扩展**：工作量增加时，可以调整现有机器资源，或增加机器分担工作。

并发是一种组织和推进多项工作的方式。它让系统有机会更有效地使用资源，但拆分和协调本身也会带来成本，所以并发设计要结合实际瓶颈。

## 2. 用延迟和吞吐量看性能

“系统变快了”需要具体指标说明。常见的两个视角是延迟和吞吐量：

| 指标 | 要回答的问题 | AI 服务例子 |
| --- | --- | --- |
| 延迟（latency） | 一项工作从开始到完成用了多久？ | 一个推理请求从到达到返回结果花了 800 毫秒 |
| 吞吐量（throughput） | 一段时间内完成了多少工作？ | 推理服务每秒完成了多少个请求或生成多少 token |

可以把它想成餐厅：

- 延迟是一个顾客从点单到拿到餐的时间。
- 吞吐量是一小时内厨房完成的订单数。

并发可能让厨房同时处理更多订单、提高吞吐量，但不一定让某个特定订单更快。增加排队或合批也可能提高设备利用率，同时让单个请求多等一会儿。因此讨论性能时要说清楚优化目标是响应时间、总体处理能力，还是二者之间的平衡。

## 3. 解决大规模问题与扩展系统

工作量和用户数增加时，系统需要扩展处理能力。常见方式有两类：

- **纵向扩展（scale up）**：给现有机器增加 CPU、内存或更强的 GPU。
- **横向扩展（scale out）**：增加机器或服务实例，将请求和工作分散给更多节点。

放到模型推理服务中，纵向扩展可能是换用显存更大或算力更强的 GPU；横向扩展可能是启动多个推理实例，再由调度器或负载均衡器把请求分配过去。

纵向扩展受单机硬件上限和成本约束；横向扩展需要额外处理负载分配、节点间通信、数据共享和故障管理。并发为扩展提供工作组织方式，但实际能提升多少仍取决于系统的瓶颈和协调成本。

## 4. 并发可以分布在不同层

“多个任务同时推进”不只发生在代码里，也涉及从硬件到应用的多个层次：

1. **硬件层**：多核 CPU、多个 GPU 计算单元等硬件可以同时执行多项操作。
2. **操作系统或运行时层**：调度器管理多个进程、线程或任务，决定它们何时使用处理器。
3. **应用层**：程序把工作表达为多个任务，说明哪些任务能够独立推进、哪些必须等待结果。

上层程序提出任务，下层运行时和硬件提供调度与执行能力。理解这些层次，可以避免把“代码里创建了很多任务”直接等同于“硬件正在同时做很多计算”。

例如，一个单核上的事件循环可以在多个网络请求之间切换，让多个请求的等待过程重叠；这属于并发。多核 CPU 或多个 GPU 计算单元在同一时刻执行彼此独立的计算，才是硬件层面的并行执行。

## 5. 放到 AI Infra 中理解

AI Infra 服务通常面对持续到来的请求，每个请求可能经历排队、模型计算、网络传输和结果返回。基础设施需要关心：

- 请求并发增加时，系统吞吐量如何变化？
- GPU 是否忙于计算，还是有时间花在数据传输或等待上？
- 单机资源能否解决瓶颈，还是需要增加推理实例？
- 增加实例后，负载分配和通信成本是否抵消了收益？

因此，并发不是单独的“代码技巧”，而是连接应用工作负载、运行时调度和硬件资源的系统问题。后续学习模型服务、GPU 调度和分布式部署时，这一章的延迟、吞吐和扩展视角会继续用到。

## 6. 本章记忆卡

- **并发**：组织多个任务，让它们的执行进度在时间上重叠。
- **延迟**：单项工作从开始到完成的时间。
- **吞吐量**：单位时间内系统完成的工作量。
- **纵向扩展**：增强单台机器。
- **横向扩展**：增加机器或实例并分摊工作。
- **系统视角**：并发跨越应用、运行时/操作系统和硬件，不能只看代码层。

### 面试表达

> 我把并发看成系统组织多项工作的方式，重点是让多个任务在重叠的时间段里取得进展。评价效果时要分开看延迟和吞吐：延迟关注一个请求完成得多快，吞吐关注单位时间完成多少工作。AI 推理服务扩展时还要判断瓶颈是在单机资源，还是需要横向增加实例；增加并发度后也要考虑调度和通信成本。
