# Agent 系统主线

Agent 应用不是单独一个大模型调用。它把模型、上下文、工具、外部知识、状态管理和服务接口组合成一个可运行的闭环。学习各个组件前，先看一条完整请求如何经过系统。

## 一次请求的执行顺序

以 EchoMind 的客服对话为例：

1. **接收请求**：FastAPI 接收 HTTP 请求，Pydantic 把 JSON 解析成有字段定义的请求模型。
2. **读取上下文**：系统从 Redis 读取当前会话近期消息和摘要；从 ChromaDB 读取与问题相关的历史记忆和用户画像。
3. **理解和路由**：意图识别器判断用户要解决的问题，编排器选出主 Agent，必要时加入辅助 Agent。
4. **决定是否行动**：模型根据问题、上下文和可用工具说明，返回回答文本或结构化工具调用。
5. **执行工具**：应用检查工具白名单和参数 schema，运行查询或知识库检索。
6. **观察结果并继续**：工具结果或错误返回给模型，模型可以据此补充行动或组织回答。
7. **输出与写回**：FastAPI 返回结构化响应；用户与助手消息写入 Redis，画像在后台更新。
8. **记录执行过程**：工具轨迹、耗时、错误和 Prometheus 指标用于调试与运维。

这条链可抽象为：

**请求 → 上下文 → 决策 → 行动 → 观察 → 回答 → 状态写回与追踪**

## 两个项目的系统重心

### Enterprise Insight Agent

项目一面向企业研究和竞品分析。当前工作区的主路径是网页研究：任务进入 FastAPI 后，由 IntelligenceWorkflow 调用 GPT Researcher 执行研究；页面内容经过语义相关性筛选和来源可信度排序，形成带来源的证据，再进入报告生成和证据检查。

它的“任务感知”主要影响证据选择策略。当前工作区中，Redis 和 ChromaDB 都不是默认企业研究检索底座。

### EchoMind

项目二面向客服对话。它把 FastAPI、意图识别、Agent 路由、工具调用、ChromaDB 知识库、Redis 短期记忆、ChromaDB 长期记忆以及 Trace / Prometheus 串在一次请求里。AgentOrchestrator 的工具调用闭环由项目代码自己管理。

## 组件之间的边界

- **ReAct** 描述模型如何在判断、行动和观察结果之间循环。
- **MCP** 定义外部工具服务如何被发现和调用；它解决互操作问题。
- **RAG** 描述如何先检索外部内容，再把内容交给模型生成。
- **Redis** 适合快速读写有时效的会话状态；**ChromaDB** 适合语义近邻检索。
- **FastAPI** 提供 HTTP 服务；**Pydantic** 定义数据边界；**REST** 是接口设计风格。
- **Trace 和指标**帮助判断一次请求在哪一步产生了结果或故障。

这些组件可以组合，但解决的问题不同。细节见左侧对应章节。

## 面试追问：请讲清楚 Agent 应用的一次请求

**回答：**

> 用户请求先进入服务 API 并经过结构校验。编排器读取相关会话上下文，识别意图并选择负责的 Agent。模型根据当前上下文和可用工具决定直接回答还是发起工具调用；应用校验工具名和参数后执行，把结果作为下一轮上下文返回模型。模型基于结果生成回答，服务写回工作记忆并记录工具调用 Trace。检索、状态保存、工具协议和服务接口分别由不同组件负责，因此排查问题时也可以沿着这条链定位。
