# 意图识别与 Agent 路由

## 1. 意图识别在 Agent 系统里的位置

意图识别判断用户当前希望完成什么任务，例如查物流、申请退货、咨询商品知识或转人工。它属于请求理解与路由层，为后续 Agent、工具或检索策略选择提供输入。

意图识别与 RAG、ReAct 分工不同：

- **意图识别**判断要走哪条业务路径。
- **RAG**从知识资料中召回支持回答的内容。
- **ReAct**让模型在工具行动和结果观察之间继续决策。
- **Trace**记录请求实际经过的分类、路由与工具步骤。

在客服 Agent 中，错误路由会让正确工具没有被调用；路由准确率因此影响知识召回、业务执行和最终答复。

## 2. EchoMind 的三路意图识别

IntentRecognizer 综合三种基线信号：

1. **LLM 分类**：利用语境处理表达灵活、需要理解上下文的请求。
2. **Embedding 分类**：把用户表达与意图样例映射到向量空间，按相似度找候选类别。
3. **Pattern 规则**：通过明确词语、编号格式和规则特征识别确定性请求，例如物流单号或强提示词。

开启 Embedding 时，基线融合权重为 LLM 0.7、Embedding 0.2、Pattern 0.1。LLM 和 Embedding 可并发计算，Pattern 路径提供快速的确定性信号。系统结合各路候选和置信度形成 baseline intent，并在 LLM 服务失败时按可用信号降级处理。

这三路不是简单把三个字符串投票：LLM、向量相似度和规则各自有不同信号含义，系统要把候选、置信度和失败状态纳入融合。


### 2.1 识别入口的缓存命中

IntentRecognizer 在执行三路识别之前先生成 cache key 并查询进程内字典。命中时立即返回之前保存的完整 IntentResult；这一轮不再调用 LLM、不再生成 query 向量、不再运行 Pattern 规则，也不会继续触发 OpenJev 仲裁。缓存只保存意图识别结果，后续 Agent 路由、知识检索、工具执行和回答生成仍照常进行。

cache key 由清理后的用户消息前 200 个字符，以及最近 3 条 history 的 role 和每条 content 前 160 个字符组成 JSON，再用 MD5 生成索引键。这里的 MD5 用于形成固定长度的字典 key，不承担密码学安全用途。相同输入上下文再次出现时，可直接复用识别结果。

这份缓存是 IntentRecognizer 实例内部的 Python 字典，不是 Redis，也不会在多个 worker 之间共享；进程重启后缓存随实例消失。recognizer 同时维护 hits、misses、size 和 hit_rate 统计，可通过 cache_stats 属性读取。

缓存容量达到 1000 条后，写入新结果前会按字典插入顺序删除最早的 500 个 key。缓存命中不会刷新 key 的顺序，因此实际淘汰行为接近批量 FIFO，而不是严格 LRU；代码中的注释写了 LRU，但没有访问顺序更新机制。当前缓存也没有按时间过期的 TTL。learn() 新增意图样例时会清空结果缓存，避免旧判断继续复用。

### 2.2 256 维字符 n-gram 哈希向量怎么生成

这一路把文本中的连续字符片段作为特征，再用哈希函数把大量可能的片段映射到固定大小的向量。它属于字符特征哈希表示，不是通过训练得到的神经网络语义 Embedding。

#### 第一步：取连续字符片段

代码将文本转成小写并去掉首尾空白，然后以滑动窗口分别抽取长度为 1、2、3 的字符片段：

- **1-gram（unigram）**：每次取 1 个字符，例如“显示签收但没收到”中的“显”“示”“签”“收”“但”“没”“到”。
- **2-gram（bigram）**：窗口每次向前移动 1 个字符，取相邻 2 个字符，例如“显示”“示签”“签收”“收但”“但没”“没收”“收到”。
- **3-gram（trigram）**：同样滑动取连续 3 个字符，例如“显示签”“示签收”“签收但”“收但没”“但没收”“没收到”。

这是按字符切片，不先调用中文分词器。“签收”会作为一个 bigram 特征，“显示签”会作为一个 trigram 特征。1、2、3-gram 同时使用，能把单字、常见搭配和较短短语的信息放进同一表示中。

项目把抽取结果放入 set，因此相同 n-gram 在同一条文本中只保留一次，不按出现次数重复累加。当前实现表达的是“哪些短片段出现过”，不是它们各自出现了几次。

#### 第二步：把 n-gram 哈希到 256 个桶

向量先初始化为 256 个 0。对每个不同的 n-gram：

1. 把 n-gram 编成 UTF-8 字节并计算 MD5 摘要。
2. 取摘要前 4 个字节转成整数，再对 256 取模，得到目标下标。
3. 查看摘要第 5 个字节的奇偶，决定本次加 1 还是减 1。
4. 在目标下标上累加这个正负值。

这种正负号哈希称为 signed feature hashing。256 表示向量固定有 256 个位置，也可以理解成 256 个哈希桶；它不是文本只有 256 个 n-gram，也不是训练出来的 256 个语义维度。不同 n-gram 可能落在同一个桶里并相互累加或抵消，这种现象叫哈希碰撞。固定维度让每条文本的表示长度一致、无需维护巨大词表，代价是不同特征会共享桶。

#### 第三步：用余弦相似度匹配意图样例

IntentRecognizer 在首次需要时，懒加载并缓存各意图模板的向量。它也把用户消息转成同一方式的向量，然后与每条模板向量计算余弦相似度；每个意图取其最相近的模板分数，再选分数最高的意图作为 Embedding 分支候选。

因此，这一路的判断逻辑是：

**用户消息 → 字符 n-gram 特征 → 256 桶哈希向量 → 与各意图模板向量算 cosine → 选最相似的候选意图**

它可以利用相同字词、相邻字词和短字符片段的重合，适合作为轻量本地匹配信号。它不会像训练好的语言模型那样理解同义改写、上下文关系和事实语义；两个表达含义相同但字面几乎不同，字符重叠少时相似度也可能偏低。

### 2.3 本地哈希、Embedding API 与 ChromaDB 的 Embedding

“Embedding 模型”和“向量数据库”是不同层次：前者把文本编码成向量，后者保存向量并提供检索、metadata 过滤和索引能力。EchoMind 把同一个“向量”概念用于两条不同链路：意图识别器在内存中比较固定意图模板；ChromaDB 为客服文档建立可查询的知识库索引。

| 方案 | 文本如何变成向量 | 在 EchoMind 中做什么 | 运行与依赖 |
| --- | --- | --- | --- |
| IntentRecognizer 本地哈希 | 1/2/3 字符 n-gram 经 MD5 signed hashing 映射到 256 维 | 用户请求和意图模板直接算 cosine，相似意图候选进入三路融合 | Python 进程内计算，无外部模型调用；轻量、确定性，但主要匹配字符片段 |
| 远端 Embedding API | 训练好的神经网络把文本编码为稠密语义向量 | 替代意图分支中的本地向量生成；代码预留了 voyage-3-lite 调用 | 需要兼容的 embeddings client、网络和凭证；具有模型推理的延迟与用量成本，语义表达能力更强 |
| ChromaDB 默认 Embedding function | 未显式传入函数时使用 Chroma 默认 all-MiniLM-L6-v2；该模型输出 384 维稠密向量 | 知识文档写入时编码并建立索引，查询时编码 query 后检索相似文档 | 负责文档向量化与索引查询；默认模型在本地/Chroma 服务侧运行，另可配置其他 embedding function |

EchoMind 的意图识别代码通过检查 client 是否提供 embeddings.create 来尝试 voyage-3-lite；当前识别器由 Anthropic SDK 的 AsyncAnthropic client 初始化，标准运行路径使用本地 256 维字符 n-gram 回退。voyage-3-lite 的远端分支是兼容 Embedding client 可用时的代码路径。该模型未指定 output_dimension 时的默认向量维度为 512。

EchoMind 的 KnowledgeBase 创建 Chroma collection 时不传 embedding_function。文档导入和 query_text 查询因此由 Chroma 的默认 Embedding function 处理；当前默认模型为 all-MiniLM-L6-v2，输出 384 维向量。ChromaDB 是存储与检索组件，它可以接收不同来源生成的向量，也能通过 embedding_function 换用其他编码模型。

三种方式的关键区别：

- **本地哈希与神经 Embedding**：哈希向量靠字符特征的共享和碰撞近似相似表达；神经 Embedding 从训练数据中学习语义空间，可让不同措辞的相近意思得到相近向量。
- **远端 API 与 Chroma 默认模型**：远端接口把文本发送给 Embedding 服务并返回向量；项目 Chroma 默认模型由 Chroma 的默认 Embedding function 计算，通常在 Chroma 运行环境本地执行。
- **IntentRecognizer 与 ChromaDB**：前者只对意图模板做直接 cosine 比较，不建向量数据库；后者将文档、向量和 metadata 持久化并建立检索索引。
- **同一比较必须处于同一向量空间**：模板和 query 要使用同一模型、兼容的配置和相同维度。切换本地哈希、Voyage 或 Chroma 默认模型时，不能把一种模型的向量拿去和另一种模型的向量直接算相似度；模板向量或 collection 索引也要使用一致的模型重建。

当前代码里两条路径不能混为一谈：IntentRecognizer 的 256 维向量用于客服意图分类；ChromaDB 的 all-MiniLM-L6-v2 向量用于客服文档与历史记忆召回。知识库和记忆的 RAG 过程见[RAG 与语义检索](rag.md)及[记忆系统：Redis 与 ChromaDB](memory.md)。

## 3. OpenJev 的选择性仲裁

OpenJev 在 EchoMind 里是基线分类之后的选择性决策服务，不是与三路基线平行的第四张选票。系统把边界案例送去仲裁，例如：

- baseline 将请求判断为 other；
- 综合置信度低于配置阈值；
- LLM、Embedding 和 Pattern 出现分歧；
- 路由错误代价较高，且当前决策需要额外判定。

如果 LLM 已以高置信度给出判断，可直接使用基线结果。OpenJev 返回有效且可识别的候选时，系统采用仲裁结果；服务失败或返回无效候选时，保留现有基线结果。响应还记录决策来源、状态和延迟，便于对比路径行为。

OpenJev 通过独立服务接口接入，不承担知识库检索，也不替代 AgentOrchestrator。它解决的是“不确定的意图如何再判一次”。

## 4. 评测结果如何解释

项目使用固定标注样本对 baseline 与 OpenJev 路径做配对比较。G5 OpenJev paired 结果包含 38 个样本；通用意图指标覆盖其中 36 个适用样本，细粒度物流意图覆盖 15 个样本：

| 指标 | Baseline | OpenJev |
| --- | ---: | ---: |
| 通用意图准确率 | 32/36 = 88.89% | 34/36 = 94.44% |
| 通用意图 Macro-F1 | 0.9065 | 0.9394 |
| 细粒度物流准确率 | 13/15 = 86.67% | 15/15 = 100% |
| 细粒度物流 Macro-F1 | 0.8714 | 1.0000 |
| 端到端延迟 P50 | 1356 ms | 1513 ms |
| 端到端延迟 P95 | 2442 ms | 7150 ms |

本轮仲裁路径触发 6 次、采纳 6 次，32 个样本跳过仲裁。结果呈现了准确率与尾延迟的业务权衡：复杂物流意图的固定样本识别更准确，同时选择性外部仲裁会增加触发请求的等待时间。配对样本、数据集哈希、触发次数和时延一起给出，能说明这组比较的样本边界与运行代价。

这组结果来自 G5 的固定数据版本。G4 的基线、物流标签扩展和本地模型评测使用不同数据版本与配置，应各自报告，不能拼成同一轮对比。完整指标见[Agent 系统评测](evaluation.md)和[项目实践：EchoMind](../projects/echomind.md)。

### 准确率和 Macro-F1 各说明什么

准确率是预测正确的样本数除以总样本数，反映总体命中比例。类别分布不均衡时，大类可能主导准确率；Macro-F1 先分别计算每一类的 F1，再对类别做等权平均，能看出模型是否忽略了小类。

因此面试汇报固定样本时，应同时说清楚数据版本、样本数、类别范围、准确率、Macro-F1，以及引入额外决策路径后的延迟。单个百分比不足以描述路由能力。

## 5. 从业务错误成本理解多路分类

不同路由错误的代价不同：

- 将知识咨询误判为物流查询，可能调用无关工具并返回无用结果。
- 将物流请求判为 other，可能让用户得不到可执行的查询。
- 将普通问候送入高成本仲裁服务，会增加延迟却没有相应收益。
- 意图标签过粗，会掩盖退款、退货、催件等细分任务在工具和流程上的差异。

所以分类设计不仅要最大化总体准确率，还要看类别召回率、错误类型、下游工具是否成功、用户是否需要再次表达，以及额外模型调用带来的延迟和成本。选择性仲裁把更高成本的判断能力集中用于风险较高的边界案例。

## 6. 面试表达

### EchoMind 的意图识别如何实现？

> 我把意图识别设计成多信号基线：LLM 理解上下文，Embedding 匹配相似表达，Pattern 识别显式规则特征，开启向量路径时权重为 0.7、0.2、0.1。LLM 和 Embedding 并发执行后融合候选与置信度。低置信度、分歧或 other 等边界案例再选择性调用 OpenJev 仲裁，确定性高的请求直接采用基线结果。最终意图进入 Agent 路由，并在 Trace 中保留来源、状态和耗时。

### OpenJev 是不是第四路投票？

> 它承担下游选择性仲裁，不与三路基线等权投票。三路基线先给出候选和置信度，OpenJev 只处理配置的边界案例；高置信结果会跳过，以控制额外调用成本和延迟。

### 如何说明 OpenJev 的评测结果？

> G5 配对样本共 38 条，通用标签适用样本是 36 条，baseline 准确率 88.89%、Macro-F1 0.9065；OpenJev 路径是 94.44%、0.9394。细粒度物流 15 条从 86.67% 提升到 100%。仲裁触发 6 次、跳过 32 次；端到端 P95 从约 2.44 秒变成 7.15 秒。这让准确率收益、覆盖样本和尾延迟都能被清楚讨论。

### 意图识别和 RAG 有什么区别？

> 意图识别决定系统要处理什么任务以及进入哪个 Agent；RAG 决定为了回答该任务要从资料中取回哪些证据。比如识别为商品规则咨询后，Agent 可以进一步调用 RAG 查对应政策，两者前后协作但不是同一种检索。


## 7. 面试补充问答：缓存和三种向量路径

### 意图识别开头的缓存做什么？

> IntentRecognizer 会先用当前消息和最近 history 生成 key。命中时返回之前缓存的 IntentResult，直接跳过 LLM、Embedding、Pattern 和 OpenJev；未命中才执行完整识别链。缓存的是意图判断，不是客服回答，所以后续 Agent、RAG 和工具仍会运行。它是进程内缓存，容量达到 1000 后按插入顺序批量淘汰一半，没有 TTL；多 worker 各有自己的缓存。

### 256 维 n-gram 向量里的“256”是什么意思？

> 它是哈希桶数量。程序把唯一的 1、2、3 字符片段各自哈希到 256 个位置，并用正负号累加，因此输出始终是 256 维。不同片段会碰撞到同一个桶；它不是 256 个可解释词，也不是模型训练出来的 256 维语义向量。

### 本地哈希与远端 Embedding 有什么区别？

> 本地哈希按字符片段构造特征，不加载神经网络，也不访问外部服务；它便宜、快速，适合给意图分类提供轻量字面相似信号。远端 Embedding API 由训练好的模型生成稠密语义向量，对同义改写和上下文表达的泛化更强，但增加网络调用、延迟、用量成本和外部服务依赖。项目代码为远端分支预留 voyage-3-lite，目前标准 Anthropic client 下走本地回退。

### ChromaDB 是不是 Embedding 模型？

> 不是。ChromaDB 是向量存储和检索组件；collection 没有传自定义 embedding_function 时会采用默认 all-MiniLM-L6-v2 编码。EchoMind 的知识库通过 Chroma 写入文档向量并查询相似文档；IntentRecognizer 则另行用本地 256 维哈希向量匹配意图模板。
