# RAG 与语义检索

## 1. RAG 在 Agent 系统中的位置

RAG（Retrieval-Augmented Generation，检索增强生成）先从外部资料中找到与问题相关的内容，再把这些内容连同用户问题交给模型生成回答。它让模型可以使用项目文档、业务知识或实时网页等外部信息，并让答案有可追溯的依据。

RAG 是一条完整的数据链，不等于向量数据库：

**资料接入 → 清洗切块 → Embedding → 建立索引 → 查询改写 → 召回候选 → 过滤与重排 → 组装证据上下文 → 生成 → 证据检查**

Embedding 把文本映射成向量，向量索引按距离找候选。语义近邻表示文本在向量空间中接近，不等于事实正确，也不保证片段完整回答了问题。因此，RAG 质量同时取决于语料、切块、Embedding、召回、排序、上下文组织和生成后的核验。

## 2. 从文本到语义召回

### 2.1 切块为何重要

长文档不能整体塞进每一次模型请求。系统会先把它拆成较小片段，并为片段保留标题、来源、位置等 metadata。切得太大，相关信息容易被无关段落稀释；切得太小，定义、条件和结论可能被拆散。Overlap 可让相邻块共享边界内容，减少跨块上下文断裂，但会增加重复量。

切块大小应按语料结构和检索问题评估，而不是把某个字符数当成通用最优值。

### 2.2 Embedding 与距离

Embedding 模型把 query 和文档片段编码到兼容的向量空间。检索器依照索引配置的距离度量，返回最接近的候选。Top-K 表示候选个数；如果需要排除不够相关的结果，还需设计最低分数、业务过滤或无结果处理。

关键词检索擅长精确名称和编号，向量检索擅长表达不同但语义相近的问题。混合检索可以先综合两种信号，再对候选重排。Reranker 通常比较 query 与每条候选的匹配程度，帮助把更有用的证据放在上下文前面。

## 3. EchoMind：客服知识库 RAG

知识库实现在 mcp/knowledge_base.py，工具层连接 mcp/tool_manager.py，Agent 工具注册和 API 位于 agents/tools.py 与 api/main.py。

### 3.1 文档导入

1. 输入文档的 title 和 content。
2. 切分器按中文句号与换行累计句子，目标块长约 500 个字符。
3. 每块保留标题、chunk_index 和 total_chunks 等 metadata。
4. ChromaDB collection 为 documents 生成向量并保存文本和 metadata。
5. 写入使用稳定 ID 与 upsert，重复导入可更新对应记录。

这是句子累计式切分，不使用 overlap，也不是按 token 数精确截断；一条很长的句子可以让块超过目标长度。块大小和边界质量要用客服问题与标准证据评估。

### 3.2 查询、并行召回、去重与重排

EchoMind 的知识检索不只做一次单句向量查询。工具管理层会先围绕原问题生成多种查询表达，再并行发起召回；随后合并候选、按内容或标识去重，减少同一知识片段重复占位；最后可以用 LLM reranker 比较候选与原问题的匹配程度，选出有限数量的结果返回 Agent。

- **多查询改写**扩大表达覆盖，例如把“怎么退货”展开为退货条件、申请流程和时限等角度。
- **并行召回**缩短多个独立 query 的总等待时间。
- **去重**让有限上下文容纳更多独立证据。
- **重排**把粗召回阶段遗漏的相关性差异重新排序。

模型收到的检索内容作为工具 Observation，之后再据此组织客服答复。要评估这一环节，应构造代表性问题及其应命中的文档，观察 Recall@K、证据覆盖率、重复率和最终答复质量。

### 3.3 Collection 距离与分数

EchoMind 创建知识库 collection 时未显式设置距离度量，Chroma 新建 collection 默认使用 L2 距离。项目代码把 1 - distance 转成展示用 score；这个值是距离的简单变换，不是经过校准的概率或置信度。阈值判断应明确采用的距离定义，并用标注问题集校准。

项目依赖使用 Chroma 默认的 all-MiniLM-L6-v2 Embedding。向量维度和索引可正常工作说明组件接通了；中文检索效果则需要以真实中文问法和证据标注来衡量。

## 4. Enterprise Insight Agent：实时网页研究与证据

Enterprise Insight Agent 默认从网页搜索和抓取开始，不依赖预先维护的固定知识库。其检索目标是为当前研究任务寻找相关、可归因的网页证据。

### 4.1 任务感知检索链

1. ResearchTaskClassifier 根据任务内容判断研究类别，例如事实核验、技术能力分析、竞品比较、趋势研究、冲突可信度判断或企业决策建议。
2. 类别对应固定 EvidencePolicy，包含偏好的来源类型和来源权威性权重。
3. SearchAPIRetriever 获取网页候选；ContextCompressor 以约 1000 字符的块、100 字符 overlap 切分长文，再用 EmbeddingFilter 按相关性筛选，默认相似度阈值为 0.35。
4. SourceAwareScorer 将语义相似度与来源权威性组合：**score = (1 − w) × similarity + w × authority**。
5. 权重随任务类别变化，范围为 0.08 至 0.30；无法使用分类结果时采用 0.20 的中性回退权重。语义相关性始终是主信号，可靠来源在相关候选中获得排序优势。
6. 选中的证据保留来源标识和 URL，进入报告上下文和 Claim Gate 证据审查。

“来源感知重排”不意味着权威来源可以凭来源标签压过完全无关内容：先做语义相关性筛选，再在相关候选间融合来源可靠性。来源评分是排序先验，不是对网页真实性的证明。

GPT Researcher 还包含可选向量库路径；面试描述默认企业研究时，应把可选向量库和实时网页主链分开。

### 4.2 Claim-Evidence 审查

报告主张需要能回到证据。企业流程会将生成报告中的 claim 与结构化 evidence 建立联系，再由 Claim Gate 和 Grounding Validator 检查支持关系，发现缺少支持或存在冲突的条目后形成修复计划。追踪信息保存被检查的 claim ID、证据 ID、审查结果和 finding code。

这把“网页检索—证据排序—报告主张—主张审查”连成一条可追溯链路。来源链接帮助人复核原文；自动校验帮助系统发现缺少支持的主张。二者共同提升报告的可审查性。

## 5. 意图识别、RAG 与 Agent 决策的关系

EchoMind 的意图识别先判断用户想完成什么，例如物流查询或知识咨询，再由 Agent 路由决定调用哪类能力。知识库 RAG 解决的是从资料中找内容；ReAct 解决的是模型如何选择并调用工具；Trace 记录执行过程。一次请求可能依次经过这些环节，但它们回答的是不同问题。

- 意图路由：当前用户要做什么？
- RAG：哪些外部片段与问题相关？
- ReAct：是否需要工具行动，行动后如何继续？
- Trace：这一轮实际经过哪些步骤，结果和耗时如何？

更完整的系统边界见[ReAct 与工具调用](react.md)、[Trace、Span 与 Agent 轨迹](trace-observability.md)和[项目一：Enterprise Insight Agent](../projects/enterprise-insight-agent.md)。

## 6. 面试表达

### RAG 一次查询经历哪些步骤？

> 文档先经过清洗和切块，保留来源与位置 metadata，再由 Embedding 编码并写入索引。查询时系统对问题做向量化，可先改写为多个 query 并行召回；候选合并去重后再重排，最后把有限的高相关证据连同来源交给模型生成。项目评估会检查召回覆盖、证据质量和最终答案，而不只检查向量库是否返回了结果。

### Embedding、ChromaDB 和 RAG 分别做什么？

> Embedding 模型把文本变成向量；ChromaDB 保存文档、向量和 metadata，并执行向量近邻查询；RAG 是把检索接入上下文和生成的完整应用链路。三者分属表示模型、存储检索组件和系统模式。

### EchoMind 如何提高客服知识召回质量？

> 知识文档按句子边界切成约 500 字符的块并附上标题和块序号。查询时工具层围绕原问题生成多个表达、并行检索、去重，再由 LLM 重排候选。入选片段作为工具结果返回 Agent。这样分别用查询改写扩大覆盖、去重节省上下文、重排改善候选顺序；效果通过问题集的 Recall@K、证据覆盖和答复质量评价。

### Enterprise Insight Agent 的任务感知检索是什么？

> 它面向实时网页研究。系统识别研究类别后选择对应的 EvidencePolicy，网页块先按语义相关性筛选，再由 SourceAwareScorer 把相关性与来源权威性按任务权重融合排序。选中的证据和 URL 会进入报告生成及 Claim Gate 审查。因此任务类别影响来源偏好，证据则贯穿到报告主张检查。

### 如何解释向量相似度？

> 向量近邻反映 Embedding 空间中的接近程度，是候选排序信号而非事实正确率。我的项目一会对相关候选做来源感知排序；项目二当前 Chroma collection 默认采用 L2，代码把 1 减 distance 作为展示分数，所以阈值必须结合该距离定义和标注样本解释。
