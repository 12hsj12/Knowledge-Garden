# 记忆系统：Redis 与 ChromaDB

## 1. Agent 的记忆类型

Agent 的记忆由多种读写模式组成：

- **工作记忆**保存当前会话最近的消息，按会话快速读取。
- **摘要记忆**压缩较早对话，控制上下文长度。
- **情景记忆**保存发生过的对话或事件，按语义相似度召回。
- **用户画像**保存相对稳定的偏好和实体。
- **领域知识**保存 FAQ、产品手册和业务规则。

每种记忆的时效、查询方式和可靠性要求不同。EchoMind 用 Redis 管理近期会话状态，用 ChromaDB 检索历史情景、画像和客服知识。

## 2. Redis 在 EchoMind 中的工作方式

Redis 是独立运行的内存数据结构存储，提供 List、Hash、Set、Sorted Set、Stream 等数据结构、原子操作和 TTL。项目把它用于近期工作记忆与摘要。

### 2.1 消息写入、读取和压缩

1. 会话 key 由用户和会话共同组成：wm:{user_id}:{conv_id}。
2. 新消息用 LPUSH 写入 Redis List，最新消息位于列表前端。
3. 读取最近消息后反转排列，按时间从旧到新交给上下文组装。
4. 工作记忆每次更新后刷新 24 小时 TTL。
5. 消息达到 COMPRESS_AT=15 时，较早消息由模型压缩为摘要；摘要以 Redis key 保存并设置 24 小时 TTL，工作列表保留最近 5 条。
6. 压缩后的情景文本还会写入 ChromaDB，便于后续按语义搜索。

因此 Redis 负责“当前窗口里按顺序读写什么”，ChromaDB 负责“过去哪些内容和这次问题语义相关”。

### 2.2 为什么用 Redis

- **读写延迟低**：近期消息频繁写入和读取，内存数据结构能支持轻量会话操作。
- **多 worker 共享状态**：多个 Python worker 连接同一 Redis 服务，可读取同一会话 key；进程重启也不会只因进程内字典消失而丢失当前 Redis 数据。
- **数据结构匹配窗口操作**：List 的 LPUSH、LRANGE 和裁剪操作比把整个对话对象反复序列化成一个值更贴合消息窗口。
- **TTL 管理会话时效**：空闲会话自动过期，降低短期状态的清理负担。
- **原子命令简化并发更新**：单条 Redis 命令由服务端原子执行，能减少多个 worker 同时更新列表时的竞争窗口；复合业务更新仍要根据一致性要求使用事务或 Lua 脚本。

Redis 是共享的短期状态存储，不自动等同于永久数据仓库。当前工作记忆设置 24 小时 TTL；长期合规、审计或恢复要求需要持久化数据层和备份策略共同满足。

## 3. Redis、Memcached 与进程内缓存

| 方案 | 适合的数据与访问 | 主要特点 |
| --- | --- | --- |
| Redis | 会话窗口、计数、队列、排序集合、分布式协调 | 提供丰富数据结构、TTL、原子操作和可选持久化 |
| Memcached | 简单 key-value 缓存 | 以字符串/字节值为主，擅长简单缓存读写，不提供 Redis List 这种消息窗口操作 |
| 进程内 dict | 单进程原型或局部热数据 | 访问直接，但多 worker 不共享，进程重启即丢失 |

如果只需要缓存完整序列化对象，Memcached 可以胜任；当会话读写需要 List 操作、过期管理和更多协调能力时，Redis 更贴合 EchoMind 的访问模式。

### 3.1 Key-value 与 LRU

Key-value 是一种通过唯一 key 读取 value 的基本接口形式。Redis 和 Memcached 都能以这种方式访问数据；Redis 的 value 还可以是 List、Hash 等结构。

LRU（Least Recently Used，最近最少使用）是一种容量淘汰策略：空间不足时优先清理最近最少被访问的数据。它与 TTL 的区别是，TTL 按设定的时间过期；LRU 按访问新旧和容量压力淘汰。两种规则可并存。

EchoMind 的会话 key 用 TTL 控制生命周期。意图识别器另有一个有容量上限的进程内缓存；该实现不跟踪每次命中时的访问顺序，因此准确说是有界缓存，不应把它称作严格 LRU。

## 4. 并发、并行与高并发

- **并发**指多个任务的执行区间交错推进；当某个任务等待网络或磁盘时，系统可以切换去处理另一个任务。
- **并行**指多个任务在同一时刻由多个 CPU 核或执行单元同时运行。
- **高并发**描述系统在一段时间内承接大量同时存在或密集到达请求的能力，涉及队列、连接池、限流、缓存、超时、隔离和扩展等设计。

Python asyncio 的事件循环适合编排大量 I/O 等待任务；Redis 多 worker 共享状态则解决 worker 间的数据可见性。Redis 可以帮助降低单次状态读写成本，但不会单独保证整个系统拥有高并发能力。应用仍要控制模型调用时长、连接池、限流和下游服务容量。

FastAPI 的异步执行见[服务接口：FastAPI、Pydantic 与 REST](web-api.md)。

## 5. ChromaDB 在 EchoMind 中的角色

项目按用途使用不同 collection：

- **episodic**：压缩后的对话摘要，按当前 query 检索相关历史。
- **user_profile**：LLM 提炼的用户偏好与实体。
- **knowledge_base**：客服 FAQ 和知识文档 chunk。

情景记忆检索会结合 user_id、conv_id 等 metadata；当前会话相关内容不足时，可在同一用户的其他会话中继续搜索。画像以用户为范围存取，FAQ 由知识库工具查询。

向量召回适合“换一种说法找相似内容”；Redis 的 key 查询适合“取回这个会话的最新几条”。二者互补。

## 6. 一轮对话如何组装记忆

1. MemoryManager 从 Redis 取当前会话摘要与近期消息。
2. ChromaDB 按当前 query 搜索相关历史摘要，并读取用户画像。
3. MemoryContext 将摘要、近期消息、历史片段和画像整理成模型上下文。
4. Agent 判断是否调用知识库或业务工具。
5. 用户与助手消息写入 Redis，画像更新进入后台任务。
6. 达到压缩阈值后，将早期消息归纳为摘要并写入 Redis 与 ChromaDB。

系统同时保留“最近发生了什么”和“过去有哪些相似情景”。

## 7. 面试表达

### 为什么选择 Redis 保存 Agent 工作记忆？

> EchoMind 的工作记忆是近期会话窗口，需要按 user_id 和 conv_id 隔离，持续追加消息、读取最近 N 条，并在 24 小时后过期。Redis List 与 TTL 直接匹配这些操作；独立 Redis 服务还能让多个 FastAPI worker 共享会话状态。向量数据库承担历史语义召回，长期业务记录则应由有持久化与审计要求的数据库保存。

### 高并发为什么会提到 Redis？

> 多 worker 下，进程内字典只对当前进程可见，用户下一次请求落到另一个 worker 时会拿不到同一份状态。共享 Redis 让各 worker 通过会话 key 读写一致的工作窗口。它降低状态访问成本并共享数据，但整体并发能力还取决于异步 I/O、连接池、模型响应时间、超时和限流。

### Redis 与 Memcached 如何选择？

> 两者都能做分布式缓存。Memcached 适合简单 key-value 对象缓存；EchoMind 的会话读写依赖 List、按范围读取和 TTL，因此 Redis 的数据结构更合适。选择依据是访问操作和数据语义，而不只是比较谁更快。

### Redis TTL 和 LRU 的区别是什么？

> TTL 按时间决定 key 何时失效；LRU 在容量压力下按最近使用情况淘汰数据。TTL 管生命周期，LRU 管容量，两者解决不同问题。EchoMind 工作记忆主要用 24 小时 TTL。
